# 유튜브 트렌드 학습 시스템 — 계획서 (제안, 미승인)

작성: 2026-09-18. **이 문서는 결정문이 아니라 제안이다.** `CLAUDE.md` §2.1(제품 범위
경계)·§6(승인 필요 변경)에 걸리는 항목이 여럿이라, 구현 착수 전 대표님 승인이
필요하다. 승인되면 `docs/decisions/`로 옮기고 `implementation-plan.ko.md`에
공식 Task로 편입한다.

## 0. 배경 — 대화에서 확정된 전제

- 대표님은 **교육 콘텐츠 하나만이 아니라 여러 니치를 동시에 테스트**하려 한다:
  미국주식, 40대 인생살이, 경제·부동산, 노인 대상 정부지원 정보 등.
- 모든 채널이 아직 작다(대표 채널도 구독자 5천 미만) — **본인 채널 성과만으로
  배우는 루프는 당분간 신호가 거의 없다.**
- **자동으로 유튜브를 정기·반복 방문해 다른 채널을 긁어오는 건 안 한다** — 약관
  위반 위험은 자동화 여부와 무관하게 그대로다. **대표님이 그때그때 지목하는
  레퍼런스 세션**과 **본인 채널의 공식 API 데이터**만 쓴다.
- 오늘 세션에서 별도로 진행 중인 "기억 사서"(journal → topic notes, 원자적 쓰기,
  워터마크, MERGE 원칙) 구조를 그대로 재사용한다 — 새 저장 체계를 또 만들지 않는다.

## 1. 목표

프로젝트(영상)를 만들 때 유진이 "이 니치에서 잘 먹히는 썸네일·훅·템포"를 참고해서
더 나은 판단을 내리게 한다. 니치별로 다르고, 시간이 지나며 데이터가 쌓일수록
저절로 정교해져야 한다 — 매번 사람이 다시 알려줘야 하면 이 계획의 의미가 없다.

## 2. 범위 경계 (하지 않는 것)

- 다른 채널을 자동·정기·반복으로 방문/수집하는 크롤러·스크레이퍼. **금지.**
- 얼굴 바꾸기·영상 복제 같은 Hypit류 합성. **범위 밖**(`CLAUDE.md` §2.1과 이미 논의 종료).
- 저작권 있는 썸네일 **이미지 자체**를 영구 저장·재사용. 패턴 설명(텍스트)만 남긴다.
- 다른 채널의 비공개/유료 분석 데이터. 공개 페이지에서 사람이 볼 수 있는 것만.

## 3. 구조 — 두 입력, 하나의 사서 파이프라인

```
[레퍼런스 세션]              [본인 채널 성과]
 대표님이 지목한 영상          유튜브 공식 Data/Analytics API
 (브라우저로 같이 봄)          (본인 채널만, OAuth로)
      │                              │
      ▼                              ▼
   journal 항목 (니치 태그)      journal 항목 (채널·니치 태그)
      └──────────────┬───────────────┘
                      ▼
            사서 정리 잡 (오늘 별도 작업 중인 것 재사용)
                      ▼
         니치별 주제 노트 (notes/<니치>/*.md)
                      ▼
   프로젝트 생성 시 니치를 물어보거나 추정 → 해당 노트를
   유진의 편집 판단 컨텍스트에 주입 (기존 `_memory_section`류 자리 재사용)
```

**두 입력 모두 "일지"로 들어가고, 이후 처리(정리·병합·니치별 정리)는 완전히
동일한 파이프라인을 탄다** — 사서 시스템을 두 번 만들지 않기 위한 설계다.

## 4. 데이터 모델 — 새로 필요한 것

- **프로젝트에 "니치" 태그.** 지금 project에는 이런 구분이 없다. 새 필드
  하나(`niche` 또는 `channel_id`)를 추가하고, 프로젝트 생성 시 고르게 하거나
  기본값(미지정)을 허용한다. **범위**: 이번 계획에서 가장 작고 안전한 변경.
- **레퍼런스 세션 기록 자리.** "이 영상 보니 이런 패턴이더라"를 사람이 입력하는
  가장 쉬운 방법은 **채팅**이다 — 새 UI를 만들지 않고, 대표님이 브라우저로 같이
  본 뒤 유진 채팅(또는 별도 명령형 인터페이스)에 "이건 레퍼런스로 기록해줘"라고
  하면 그 대화가 journal에 니치 태그와 함께 쌓이는 방식을 제안한다. 새 화면
  없이 기존 채팅 경로를 재사용 게이트 원칙대로 활용한다.
- **채널 등록.** 본인 채널이 여러 개(니치별로 다른 채널일 가능성이 큼)면, 채널마다
  유튜브 OAuth 인증을 따로 받아야 한다 — `CLAUDE.md` §6의 "외부 게시" 승인 계열과
  같은 절차로 다뤄야 한다.

## 5. 단계별 계획 (owner 승인 시 공식 Task로 쪼갠다)

| 단계 | 내용 | 선행조건 | 규모 추정 |
|---|---|---|---|
| P1 | 프로젝트에 니치 태그 필드 추가 (스키마·화면 드롭다운) | 없음 | 작음 |
| P2 | 레퍼런스 세션 기록 경로 (채팅에서 "레퍼런스로 기록" 트리거 → journal 저장) | 오늘 진행 중인 사서 시스템 완료 | 중간 |
| P3 | 사서 파이프라인에 니치별 분리 추가 (지금 설계는 회사 단위 하나, 여기는 니치별 여러 벌) | P2, 사서 시스템 완료 | 중간 |
| P4 | 유진 컨텍스트 주입 — 프로젝트의 니치에 맞는 노트만 골라 싣기 | P1, P3 | 작음~중간 |
| P5 | 본인 채널 성과 루프 (유튜브 Data/Analytics API 연동, 니치별) | 채널별 OAuth 승인(§6) | 큼 — 채널마다 별도 인증, 데이터가 쌓일 때까지 효과 지연 |

**권장 착수 순서**: P1 → P2 → P3 → P4로 "레퍼런스 세션" 축을 먼저 완성해서 지금
바로 가치를 내고, P5(본인 채널 루프)는 병행 착수하되 효과는 채널이 자랄 때까지
기다린다.

## 6. 리스크

- **니치가 늘어날수록 노트가 흩어져 품질이 떨어질 수 있다** — "사서" 원칙 중
  "주제 노트는 짧게, 한 주제 = 한 파일"을 니치 단위로도 지켜야 한다(니치 안에서도
  주제별로 쪼갠다: 썸네일/훅/템포/제목 각각 별도 노트).
- **레퍼런스를 따라 하다가 복제로 흐를 위험** — 패턴(구조·기법)만 뽑고 콘텐츠
  자체를 베끼지 않는다는 원칙을 사서 프롬프트에 명시해야 한다(Hypit류로 새지
  않게).
- **채널마다 별도 유튜브 인증** — 승인·크리덴셜 관리 부담이 니치 수만큼 는다.

## 7. 대표님 결정이 필요한 것

1. 지금 테스트하려는 니치 목록과, 니치마다 참고할 만한 레퍼런스 채널/영상을
   몇 개씩 미리 생각해 두셨는지 — P2 착수 전에 첫 레퍼런스 세션 대상이 필요하다.
2. 니치마다 실제로 별도 유튜브 채널을 만드실 계획인지(그러면 채널마다 별도
   인증·분석이 필요), 아니면 한 채널 안에서 콘텐츠 종류만 다양화하실 계획인지.
3. 이 계획서 전체를 승인할지, 아니면 P1~P4(레퍼런스 세션 축)만 먼저 승인할지.

## 8. 재사용 원칙 확인

- 재사용: 오늘 별도로 만들고 있는 사서(journal→notes) 파이프라인을 그대로
  쓴다. 새 채팅 UI를 안 만들고 기존 유진 채팅 경로를 쓴다.
- 새로 만드는 것: 프로젝트 니치 태그(최소 스키마), 니치별 노트 분리, 유튜브
  Data/Analytics API 연동(§6 승인 후).
- 제외: 자동 크롤링·스크레이핑 전부, 다른 채널 이미지 영구 저장.
