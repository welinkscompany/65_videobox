# 방치된 로컬 브랜치 4개 검토 (2026-09-19)

## 배경

2026-09-19 worktree 정리 중, main에 한 번도 병합되지 않은 채 남아 있던 로컬
브랜치 4개를 발견했다. 이 문서는 각각을 조사해 "합칠지/버릴지/다시 만들지"를
판단한 결과다. **이번 조사에서는 아무것도 병합하지 않았다** — 원본 4개
브랜치는 main에 그대로 남아 있고, 삭제는 대표님 승인 뒤에 한다.

## 핵심 결론 (먼저 요약)

4개 전부 **이미 main에 내용이 통째로 들어가 있다.** 브랜치 포인터만 낡았을
뿐, 커밋이 가리키는 코드 변경은 이후 다른 세션이 같은 메시지·같은 diff로
main에 다시 커밋했다(해시만 다르다 — cherry-pick이나 별도 재작업으로 보인다).
`git merge-base --is-ancestor <낡은 브랜치 커밋> main`이 4개 전부 **YES**를
반환했고, 터치한 파일만 좁혀 diff를 떠 보면 3개는 **완전히 빈 diff**(바이트
단위로 동일), 1개(바퀴 확대)는 main 쪽이 **더 발전한 상위 호환**이었다.

**권고: 4개 전부 폐기(삭제).** 재작업할 내용이 없다 — 할 일이 이미 다 끝나
있다.

## 조사 방법

- `git log --oneline main..<branch>` — main에 없는 커밋만 추출.
- `git merge-base main <branch>` — 갈라진 지점 확인, `git rev-list --count`로
  main이 그 뒤로 얼마나 더 나갔는지 측정.
- `git log --oneline --all --grep <같은 핵심 문구>` — 전체 저장소(모든 로컬
  브랜치)에서 같은 문제를 다룬 커밋을 찾음. 4개 전부 **같은 커밋 메시지를 쓴
  다른 해시**가 이미 main 계보에 존재했다.
- `git merge-base --is-ancestor <그 커밋> main` — main에 실제로 들어가 있는지
  확인 (4개 전부 exit 0 = YES).
- `git diff <낡은 커밋> <main측 매칭 커밋> -- <실제로 건드린 파일>` — diff가
  비면 완전히 같은 수정, 남으면 main이 더 나간 것.
- 바퀴 브랜치 하나는 실제로 `git rebase main`을 임시 브랜치에서 시도해 충돌
  성격을 확인한 뒤 `--abort`로 되돌리고 임시 브랜치를 지웠다.

## 1. `worktree-agent-a1c8831a1cf4bd9e0` — 타임라인 바퀴 확대·축소

- 커밋: `62691fd7b` (2026-09-12) "타임라인을 바퀴로 늘리고 옆으로 민다 --
  캡컷과 같은 Ctrl+바퀴, Shift+바퀴"
- 갈라진 지점(`3a90e1cc6`) 이후 main은 74개 커밋 더 나갔다.

**안 합쳐진 이유(확인된 사실):** 같은 문구·같은 문제의식을 담은 커밋
`d5c4c6a95`가 이미 main 계보에 있다. `TimelineDock.tsx`에 Ctrl+바퀴/Shift+바퀴
로직을 넣은 diff가 낡은 브랜치와 **완전히 동일**하다(파일 단위 diff 없음).
즉 이 작업은 **이미 반영됐다** — 브랜치만 지워지지 않고 남은 것이다.

**지금도 유효한지:** main 쪽 `d5c4c6a95`는 여기서 한 걸음 더 나갔다 —
`zoomCommand` prop을 추가해 **유진 채팅 명령도 같은 `runZoom` 표를 타게** 했다
(task-3-brief.md 근거, "유진에게 말하는 거 외에도 내가 직접 조작할 수 있게").
낡은 브랜치는 마우스 조작만 담당했고, main은 그걸 포함해 채팅 경로까지
배선했다 — **상위 호환**.

**rebase 충돌 정도:** 실측함. `git rebase main`을 시도하자
`TimelineDock.tsx`에서 CONFLICT(정확히는 main이 같은 자리를 더 크게 고쳐
써서 겹침) — 예상대로 "이미 한 일을 다시 하려다 부딪히는" 충돌이었다.
`--abort`로 되돌리고 임시 브랜치는 지웠다.

**검증 상태:** 낡은 브랜치 자체는 TDD 흔적(테스트 diff 포함)이 있었지만,
지금 기준으로는 의미 없다 — 실제로 살아있는 코드는 main 쪽이다.

**권고: 폐기.** 병합하면 이미 main에 있는 것과 충돌만 나고, 남길 실질 내용이
없다.

## 왜 이런 일이 생겼는가 (추정)

4개 다 같은 패턴이다 — 격리 worktree/에이전트 브랜치에서 작업한 뒤, 그 내용을
**같은 커밋 메시지로 다시 커밋해 main에 병합**(cherry-pick 또는 별도 재작성)
했지만, **원본 worktree 브랜치 자체를 지우는 절차가 빠졌다.** `work-routes`의
`resolveProjectStage`/`work`의 "후보 결과 미리보기"는 작성자 이메일이 각각
`welinkscamp@gmail.com`/`welinkscompany@users.noreply.github.com`으로 다른데,
main에 들어간 `c4f156510` 등도 같은 계정으로 기록돼 있어 — 별도 PR이나
worktree 병합 스크립트가 브랜치 삭제를 누락한 것으로 보인다(CLAUDE.md
§3에 "병렬 작업이 필요하면 그때그때 격리 worktree를 새로 만들어 쓰고,
끝나면 병합 후 지운다"는 원칙이 있는데, 지우는 절차만 빠진 사례).
