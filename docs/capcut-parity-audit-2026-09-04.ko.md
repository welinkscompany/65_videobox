# 캡컷 1:1 대조 점검표 (2026-09-04)

owner 지시로 만든 점검표다. **고치기 전에 먼저 무엇이 얼마나 다른지 재는 것**이
목적이고, 순서는 owner가 이 표를 보고 정한다.

## 0. 이 문서가 생긴 이유

owner가 실제로 제품을 쓰면서 이렇게 말했다.

> "지금까지 너가 만든게 너무 다루기도 어렵고, 프로그램 기능 버튼도 ux / ui 가
> 너무 안좋아서, 문제가 심각해보여"
> "너가 만든 인터페이스 들이 너무 복잡하고 너 마음대로 만들어놔서 헷깔려,
> 기능이 아무리 잘 만들어져도 그걸 사용하는 사람이 헷깔리면 쓸수가 없잖아."

**지적이 맞다. 그리고 이건 취향 문제가 아니라 승인된 결정을 안 지킨 문제다.**
`CLAUDE.md` §2.1은 "캡컷을 벤치마킹한다. 생김새는 거의 동일하게"라고 못박았고
`decisions/2026-08-30-capcut-button-level-parity.ko.md`는 버튼 단위까지 맞추라고
했다. 그런데 실제로는 그 기준을 따르는 대신 새 구조를 만들어 넣었다.

owner의 후속 지시(2026-09-04):

- **웹 버전은 그냥 캡컷을 벤치마킹한다. 버튼 이름과 내용도 동일하게.**
- **AI(로컬·Hermes 유진)는 뼈대가 아니라 옆에서 도와주는 역할로 둔다.**
- `이야기` 단계는 **편집기 안 도구로 옮긴다.**
- 색·팔레트는 그대로 둔다(§6 승인 대상이라 건드리지 않음).

## 1. 잰 방법

캡컷 쪽은 owner가 로컬에 설치해 둔 `Wbrowser`(CDP 9222 / 엔진 7981)로 **owner가
이미 로그인해 둔 실제 편집기 탭**을 넘겨받아 쟀다. owner가 명시적으로 지시했고
("너가 편집 테스트 같은거 다 해봐도 되"), 읽기와 탭 전환만 했다.

우리 쪽은 배포된 컨테이너(`127.0.0.1:5173`)에서 실제로 프로젝트를 만들고 밟으며
쟀다. **이 문서의 숫자는 전부 실측이다. 짐작한 값은 없다.**

캡처: `docs/references/capcut/2026-09-04-editor-text-panel.png`(패널 열린 상태),
`2026-09-04-editor-panel-collapsed.png`(접힌 상태).

## 2. 제일 큰 차이 — 치수

| 항목 | 캡컷 | 우리 | 차이 |
|---|---|---|---|
| 기준 글자(`html`/`body`) | **12px** | **16px** | 우리가 **33% 큼** |
| 화면에서 제일 많이 쓰는 크기 | 14px(63곳) · 12px(39곳) | 16px 기준 척도 | |
| 버튼 높이 | **32px로 통일**(15개가 정확히 32) | 28 · 29 · 32 · 36 · 52 뒤섞임 | 우리는 제각각 |
| 제일 큰 버튼 | 50px(`내보내기` 하나뿐) | 80px(`+ 새 프로젝트 만들기`) | |

**owner가 말한 "글자가 커서 버튼이 다 커지고 어거지로 우겨넣게 된다"의 정체가
이것이다.** 기준이 16px이면 같은 정보에 화면을 1.3~2배 쓰게 되고, 그러면 자리가
모자라 스크롤이 생기고, 스크롤을 없애려고 탭으로 우겨넣는 악순환이 된다.

버튼 높이가 제각각인 것도 별개 문제다. 캡컷은 32px 하나로 간다.

## 3. 배치 — 세로 띠 vs 가로 탭

**캡컷은 이동을 세로 아이콘 띠로 한다. 우리는 가로 탭으로 한다.** 이게 스크롤이
생기는 구조적 이유다. 가로 폭은 남고 세로 폭은 늘 모자란데, 우리는 세로를 쓰고
캡컷은 가로를 쓴다.

캡컷 편집기(1672×771 기준):

| 영역 | 폭 | 내용 |
|---|---|---|
| 왼쪽 아이콘 띠 | ~72px | 미디어·템플릿·요소·오디오·텍스트·캡션·대본·편집효과·전환·필터 … **12개** |
| 그 옆 패널 | ~293px | 지금 고른 띠 항목의 내용만 |
| 가운데 | 나머지 | 미리보기 + 그 아래 타임라인 |
| 오른쪽 속성 패널 | ~266px | **지금 고른 속성 묶음 하나만** |
| 오른쪽 아이콘 띠 | ~57px | 사전 설정 · 기본 · 텍스트에서 음성으로 · 애니메이션 |

우리 편집기:

| 영역 | 상태 |
|---|---|
| 왼쪽 | 가로 탭 **4개**(미디어·오디오·자막·전환), 내용은 세로로 쌓임 |
| 오른쪽 | 세부 정보 칸이 **보이는 높이의 2.44배**(433px 창에 1055px) → 스크롤 |

**핵심:** 캡컷 오른쪽 속성 패널이 짧은 이유는 내용이 적어서가 아니라, 다른
속성 묶음들이 **아래로 쌓이지 않고 오른쪽 세로 띠로 빠져 있기** 때문이다.
owner가 "스크롤 내리지 말고 탭으로 정리하라"고 한 게 정확히 이 구조다.

그리고 **캡컷은 패널을 접을 수 있다**(왼쪽 가장자리 `›` 손잡이). 접으면 미리보기와
타임라인이 화면을 다 쓴다. 우리에겐 없다.

## 4. 이름 — 버튼 이름을 캡컷과 맞춘다

owner 지시: "그냥 캡컷하고 버튼 이름이나 내용도 동일하게 만들어".

캡컷 편집기 왼쪽 띠(실제로 읽은 값):

```
미디어 · 템플릿 · 요소 · 오디오 · 텍스트 · 캡션 · 대본 · 편집효과 · 전환 · 필터 · 브랜드 키트 · 플러그인
```

캡컷 오른쪽 속성 띠: `사전 설정 · 기본 · 텍스트에서 음성으로 · 애니메이션`
캡컷 속성 항목: `변형 · 확대(%) · 위치(X, Y) · 회전(°) · 브랜드 키트에 추가`
캡컷 상단 오른쪽: `업그레이드 · 내보내기`
캡컷 공개 사이트 기능명: `자동 캡션 · 캡션 템플릿 · 텍스트에서 음성으로 ·
사용자 지정 음성 · 음성 보정 · 노이즈 제거 · 동영상 길이 다듬기 · 품질 보정`

바꿔야 할 이름(우리 → 캡컷):

| 우리 | 캡컷 | 비고 |
|---|---|---|
| 자막 | **캡션** | 캡컷은 `텍스트`(화면 위 글자)와 `캡션`(자막)을 **따로 둔다**. 우리는 하나로 뭉쳐 있다 |
| 자막 만들기 | **자동 캡션** | |
| 내레이션 | **텍스트에서 음성으로** | |
| 목소리 등록·클론 | **사용자 지정 음성** | |
| 완성본 만들기 / 내보내기 | **내보내기** | 하나로 |
| 세부 정보 | **기본** (+ 속성 띠로 분리) | |

**캡컷에 없는 것**은 이름을 가져올 데가 없다 — `유진`, `동영상 번역기`,
`촬영본 정리`가 그렇다. 이건 캡컷 자리에 억지로 끼우지 말고 별도로 정한다.
반대로 **우리에 없는 캡컷 항목**(템플릿·요소·편집효과·필터·브랜드 키트·플러그인)은
`decisions/2026-08-30`의 "없는 기능 버튼은 안 만든다"에 따라 만들지 않는다.

## 5. 흐름 — 입구가 틀렸다

실제로 새 프로젝트를 만들어 끝까지 밟으며 잰 것.

| 단계 | 실측 | 문제 |
|---|---|---|
| 첫 화면 | 누를 수 있는 것 **103개**(한 화면에 22개), 시작 경로 **3개 병렬** | 캡컷은 `+ 새로 만들기` **하나** |
| 프로젝트 생성 | **6.2초** 뒤 편집기 직행 | `이야기`를 건너뛴다 (`AppRouter.tsx:318` `goToNewProject`가 `section:"editor"` 하드코딩) |
| 그 편집기 첫 화면 | "미리보기를 만들지 못했어요" **오류 2개** + "일치하는 미디어가 없어요" | 새 프로젝트 첫인상이 오류 화면 |
| `이야기`(직접 찾아가야 함) | 갈래 4개 → 유진 질문 4개 → 요약 승인 → 소리 갈래 3개 | 편집 시작 전에 결정 6~7번 |
| 초안 직전 | **"이 초안은 내보낼 수 없어요"** + 장면마다 컨트롤 7개 × 장면 수 | 대본만 넣고 온 사람의 첫 결과가 "안 된다" |
| 단계 이동 | 4.5초 | |

**`이야기` 단계 자체는 잘 만들어져 있다**(대본 붙여넣기 / 찍어둔 영상 / 목소리만 /
아무것도 없음). 문제는 **입구가 거기로 안 보내고**, 대신 빈 편집기에 오류를 띄운 채
떨어뜨린다는 것이다. owner가 "뭘 눌러야 할지 모르겠다"고 한 게 이것이다.

캡컷은 **`대본`이 편집기 왼쪽 띠 항목**이다. owner가 정한 "이야기를 편집기 안
도구로 옮기기"가 캡컷 구조와 정확히 같다.

## 6. 없는 기능 / 안 보이는 기능

| owner 지적 | 실측 결과 |
|---|---|
| 스페이스바로 멈춰야 하는데 안 됨 | **기능은 있다.** `preview-stage.tsx:206`이 `window`에 전역으로 듣는다. 다만 `currentMedia`가 없으면 **재생줄 자체가 안 그려진다**(`:250`) — 미리보기가 실패한 화면에서는 재생기가 통째로 사라져서 눌러도 아무 일이 없다 |
| 드래그앤드롭이 안 됨 | **바깥 파일 끌어다 놓기가 없다.** `dataTransfer.files` 처리가 0곳. 내부 자료 카드 → 타임라인은 있다(`TimelineDock.tsx:841`) |
| 글꼴 드롭다운 무시됨 | 글꼴 **15개는 이미 있다**(본문·명조·제목·손글씨). 다만 드롭다운이 아니라 `<ul>` 버튼 목록이라 세로를 크게 먹는다 |
| 영상 불러오기가 느림 | 아직 원인 안 쟀다. **짐작하지 않는다** |
| 1초 단위 재생이 느림 | 아직 원인 안 쟀다 |

## 7. 순서 제안 (owner가 정한다)

뿌리부터 잡아야 뒤엣것이 저절로 풀리는 순서로 적는다.

1. **치수 기준을 캡컷에 맞춘다** — 기준 글자 16px → 12px, 버튼 높이 32px 통일.
   이게 스크롤·우겨넣기의 뿌리라 **먼저 하면 3·6번 일이 줄어든다.** 다만 화면
   전체가 한꺼번에 바뀌므로 되돌리기 쉽게 따로 커밋한다.
2. **입구를 고친다** — `+ 새로 만들기` 하나로. 프로젝트를 만들면 편집기로 가되
   빈 화면에 오류를 띄우지 않는다. `이야기`는 편집기 안 `대본` 항목으로 옮긴다.
3. **왼쪽 가로 탭 → 세로 아이콘 띠**, 오른쪽 세부 정보는 **속성 세로 띠**로 쪼개
   스크롤을 없앤다. 패널 접기 손잡이도 같이.
4. **이름을 캡컷과 맞춘다**(§4 표).
5. **바깥 파일 끌어다 놓기**를 넣는다. 업로드 경로는 이미 있으니 붙이는 일이다.
6. **글꼴을 드롭다운으로** 바꾼다.
7. **느림의 원인을 잰다** — 영상 불러오기, 1초 이동. 재고 나서 고친다.

지키는 것: 색·팔레트는 그대로(§6). 사람 게이트 셋(제목 선택·대본 확정·업로드)은
없애지 않는다(`decisions/2026-08-16`). 캡컷에 없는 기능 버튼은 새로 만들지 않는다
(`decisions/2026-08-30`).

## 8. 이 점검표의 한계

- 캡컷 쪽은 **편집기 화면 하나**를 봤다. 내보내기 화면·미디어 패널·캡션 패널은
  아직 안 열어 봤다. 필요하면 같은 방법으로 더 잴 수 있다.
- 우리 쪽 "느리다"는 아직 **안 쟀다**. §6에 그렇게 적어 뒀고, 재기 전에는
  원인을 말하지 않는다.
- 이 문서는 **무엇이 다른지**만 적었다. 어떻게 고칠지의 구체안은 owner가 순서를
  정한 뒤에 쓴다.
