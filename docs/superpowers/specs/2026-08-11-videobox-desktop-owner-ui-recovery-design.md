# VideoBox PC 전용 owner UI 복구 설계

- 상태: owner 검토 대기
- 작성일: 2026-08-11
- 대상 브랜치: `codex/videobox-container-compatibility`
- 대상 환경: PC 편집 전용 웹 UI

## 1. 결정

VideoBox의 현재 UI를 전면 재설계하지 않고, owner가 PC 화면에서 실제로 사용할 수 있게 만드는 세 가지 복구 작업을 순서대로 진행한다.

1. 제품 셸과 사이드바의 폭·정렬·축소 상태를 복구한다.
2. 자산 화면을 목적별 탭과 제한된 카드 그리드로 재구성한다.
3. 편집기 작업공간의 폭과 스크롤 소유권을 명확히 해 문서 전체 오버플로를 제거한다.

모바일·태블릿 UX는 이번 범위에서 제외한다. 기존 모바일 자동화 테스트가 있다면 회귀 탐지 목적으로 실행할 수 있지만, 모바일 화면을 새로 설계하거나 모바일 사용성을 완료 조건으로 주장하지 않는다.

## 2. 배경과 확인된 문제

실행 중인 사이트를 실제 브라우저로 확인한 결과, 테스트 통과 여부와 별개로 owner 사용을 막는 문제가 확인됐다.

- 자산 화면의 문서 높이가 약 28,000px까지 늘어난다. 음악·효과음 항목 약 130개를 한 번에 DOM에 렌더링하고, 업로드·수집함·라이브러리·프로젝트 자산·분석 영역을 한 페이지에 연속 배치한 것이 주원인이다.
- 1280px 폭의 편집기에서 문서 너비가 약 2,236px까지 늘어나 가로 스크롤이 페이지 전체에 생긴다.
- 데스크톱 사이드바의 프로젝트 행에서 선택·보관·삭제 버튼 모두 `width: 100%`를 적용받아 사이드바 밖으로 빠져나간다.
- 편집기 축소 사이드바는 아이콘 없이 텍스트만 남아 한국어 라벨이 세로로 감기고, 실제 메뉴처럼 읽히지 않는다.
- 자산 후보 카드가 파일명 위주로만 보이고 썸네일과 핵심 상태가 부족해 영상 자산을 빠르게 구분하기 어렵다.

이 문제들은 색상 팔레트나 백엔드 도메인의 문제가 아니라, 레이아웃 containment, 정보 구조, 렌더링 상한 부재의 문제다.

## 3. 준수할 승인 결정

다음 현행 결정을 변경하지 않는다.

- 캔버스 `#FAFAFA`, 강조색 `#C2410C`, 기본 텍스트 `#1C1C1E`의 white/orange 방향
- 제품 전체의 왼쪽 사이드바
- 편집기의 논리적 3열 구조
- 영상 자산의 썸네일 카드 그리드
- 1920px에서 양쪽 dock과 최소 720px preview 확보
- 1280~1599px에서 한 번에 정확히 하나의 dock을 표시하고 다른 dock은 명시적 PC 제어로 전환

새 팔레트, 새로운 주 내비게이션 경로, 새로운 디자인 시스템을 도입하지 않는다.

## 4. 목표와 비목표

### 목표

- 1920×1080, 1440×900, 1366×768, 1280×800에서 실제 브라우저로 주요 흐름을 사용할 수 있게 한다.
- 홈·자산·편집기에서 문서 전체의 가로 오버플로를 없앤다.
- 프로젝트 선택과 위험 작업을 사이드바 안에서 명확하고 안전하게 수행하게 한다.
- 자산을 종류별로 빠르게 찾고, 프로젝트 영상은 썸네일과 편집 준비 상태를 한눈에 확인하게 한다.
- 자산 수가 증가해도 한 화면의 DOM 카드 수와 문서 높이가 무제한으로 늘지 않게 한다.
- 편집기 panel과 timeline의 스크롤을 각 영역 내부에 가둔다.

### 비목표

- 모바일·태블릿 화면 설계 및 사용성 보장
- 색상 팔레트 변경
- 사이드바 주 메뉴 정보 구조나 URL 변경
- 전체 UI 또는 전역 CSS 재작성
- 백엔드 API, 데이터베이스 스키마, 자산 도메인 변경
- 편집 동작 자체를 확장하는 full NLE 개발
- 새 프런트엔드 의존성 추가
- 인증·결제 등 현재 VideoBox UI 복구와 무관한 QA 범위 확대

## 5. 검토한 접근법

### A. 세 구역 owner 사용성 복구 — 채택

사이드바, 자산, 편집기를 각각 작은 경계로 나눠 기존 컴포넌트와 API를 재사용한다. 현재 결함의 원인을 직접 제거하면서 승인된 디자인 결정과 백엔드 계약을 보존한다.

### B. 자산 화면만 우선 수정 — 기각

가장 눈에 띄는 긴 스크롤은 줄일 수 있지만, 사이드바 버튼 겹침과 편집기 가로 오버플로가 그대로 남아 owner의 실제 작업 흐름이 복구되지 않는다.

### C. 전체 디자인 재작성 및 외부 QA 체계 일괄 도입 — 기각

시각적 일관성을 새로 만들 수는 있지만 변경 범위와 회귀 위험이 크다. 현재 승인된 디자인 결정 및 저장소 운영 SSOT와도 중복될 가능성이 높다.

## 6. 상세 설계

### 6.1 제품 셸과 사이드바

#### 폭과 containment

- 일반 PC 화면의 전체 사이드바 폭은 256px로 유지한다.
- 편집기에서는 64px 축소 rail을 사용한다.
- 제품 본문은 `width: 100%`, `min-width: 0`, `box-sizing: border-box` 원칙으로 사용 가능한 폭 안에 머물게 한다.
- flex/grid 자식에는 필요한 `min-width: 0`을 적용해 긴 파일명이나 toolbar가 부모 폭을 강제로 늘리지 못하게 한다.

#### 주 내비게이션

- 기존 Lucide 아이콘을 각 메뉴에 연결한다.
- 펼친 상태에서는 아이콘과 라벨을 함께 표시한다.
- 축소 상태에서는 아이콘만 표시하고 라벨은 tooltip과 접근성 이름으로 제공한다.
- 텍스트를 폭 64px 안에서 세로로 감아 메뉴처럼 보이게 하는 방식은 사용하지 않는다.

#### 프로젝트 전환기

- 각 프로젝트 행의 주요 클릭 영역은 프로젝트 선택 하나로 제한한다.
- 보관·삭제는 행 우측의 compact `더보기` 버튼과 기존 `DropdownMenu`로 이동한다.
- 삭제와 같은 파괴 작업은 기존 2단계 확인 로직 또는 기존 확인 dialog를 그대로 사용한다.
- 백엔드 호출, 권한, 삭제 의미는 변경하지 않는다.
- 프로젝트명은 한 줄 말줄임을 적용하고 전체 이름은 tooltip 또는 title로 확인할 수 있게 한다.

### 6.2 자산 작업공간

사이드바의 기존 `자산` 경로 안에서만 동작하는 로컬 탭을 제공한다. 새 route와 API는 만들지 않는다.

#### 탭 구조

1. `내 영상` — 기본 탭. 현재 프로젝트의 영상 자산과 분석·편집 준비 상태를 통합 표시한다.
2. `음악` — 음악 라이브러리를 표시한다.
3. `효과음` — 효과음 라이브러리를 표시한다.
4. `가져오기` — 업로드 및 수집함 후보를 표시한다.

기본 화면 아래에 다른 라이브러리를 연속으로 붙이지 않는다. 탭을 선택해야 해당 종류의 자산을 렌더링한다.

#### 내 영상 카드

- 기존 `editorAssetProjection`의 썸네일 URL, orientation, audio 상태, preview URL 파생 로직을 가능한 한 재사용한다.
- 썸네일은 기존 `assetThumbnailUrl` 계약을 사용한다.
- 카드에 영상명, 재생시간, 가로/세로 방향, 오디오 유무, 분석/편집 준비 상태를 표시한다.
- 긴 파일명은 카드 폭 안에서 말줄임하고 전체 이름은 접근 가능한 이름으로 남긴다.
- 기존 페이지 하단의 별도 분석 벽은 제거하고 상태와 재시도/상세 진입을 각 자산 카드에 연결한다.

#### 음악과 효과음 카드

- 승인된 카드/그리드 방향을 유지하되 영상 썸네일을 흉내 내지 않는 compact audio card를 사용한다.
- 이름, 길이, 종류/분류, 미리듣기, 즐겨찾기 상태를 한 카드 안에서 제공한다.
- 한 페이지에 24개만 표시하는 명시적 페이지네이션을 적용하고 현재 페이지 항목만 DOM에 렌더링한다.
- 이번 범위에서는 새 virtualization 의존성을 추가하지 않는다. 현재 API가 전체 목록을 반환하더라도 DOM 렌더링은 제한한다.
- 검색 또는 필터 결과가 바뀌면 첫 페이지로 안전하게 되돌린다.

#### 가져오기

- 업로드와 수집함을 같은 목적의 탭 안에서 구분된 섹션으로 배치한다.
- 후보 카드는 데스크톱 폭에 따라 3열 또는 2열로 표시한다.
- 파일명, 크기, 가져오기 작업을 명확히 제공하고 긴 파일명이 버튼을 밀어내지 못하게 한다.
- 빈 상태, 로딩, 오류, 재시도 상태를 각 섹션 경계 안에서 표시한다.

### 6.3 PC 편집기 containment

#### 데스크톱 폭 정책

- 1920px에서는 좌측 asset dock, 중앙 preview/workbench, 우측 inspector dock을 동시에 표시하며 preview를 최소 720px로 유지한다.
- 1280~1599px에서는 한 번에 정확히 하나의 dock만 표시한다. 다른 dock은 toolbar의 명시적 PC 전환 버튼으로 연다.
- 1600~1919px도 한 dock 모드를 기본값으로 사용한다. 1920px 이상에서만 양쪽 dock을 기본 표시해 breakpoint 동작을 예측 가능하게 유지한다.
- 모바일 drawer나 touch 전용 interaction은 만들지 않는다.

#### 높이와 스크롤 소유권

- 편집기 workbench 높이는 제품 header 아래 남은 viewport에 맞춘다.
- asset dock과 inspector 내용은 각 panel 내부에서 세로 스크롤한다.
- timeline의 가로 스크롤은 timeline viewport가 소유한다.
- 문서 body와 제품 main은 편집기 때문에 가로 스크롤하지 않는다.
- asset dock에도 제한된 렌더링 또는 내부 페이지네이션을 적용해 자산 수가 문서 높이를 늘리지 못하게 한다.

#### toolbar

- 핵심 편집 작업은 한 줄에서 우선 노출한다.
- 좁은 PC 폭에서 낮은 우선순위 작업은 기존 control group 또는 더보기 메뉴로 이동한다.
- toolbar 항목 때문에 preview 최소 폭이나 문서 폭이 깨지지 않게 한다.

편집 명령, 저장, 승인, preview 의미와 API 계약은 변경하지 않는다.

## 7. 상태와 데이터 흐름

- 자산 탭, 검색/필터, 페이지 번호, 편집기 dock 선택은 프런트엔드 표현 상태다.
- 기존 API 응답을 변형하는 새 영속 상태를 만들지 않는다.
- 탭 또는 필터 전환 시 선택된 자산이 현재 결과에 없으면 명시적으로 선택을 해제한다.
- 로딩 중 기존 화면 높이가 크게 튀지 않도록 카드 skeleton 또는 고정된 빈 영역을 사용한다.
- API 오류는 해당 탭 또는 panel 안에서 표시하고 다른 주 메뉴까지 막지 않는다.
- 파괴 작업은 기존 확인과 실패 처리 경로를 유지한다.

## 8. 접근성과 문구

- 아이콘 전용 버튼에는 한국어 접근성 이름과 tooltip을 제공한다.
- 키보드로 탭, 페이지네이션, 프로젝트 메뉴, dock 전환을 사용할 수 있게 한다.
- focus ring은 현재 디자인 시스템을 유지하고 잘리지 않게 한다.
- 상태는 색상만으로 구분하지 않고 텍스트 또는 아이콘을 함께 사용한다.
- 내부 구현 용어보다 creator가 이해할 수 있는 `내 영상`, `가져오기`, `분석 중`, `편집 준비됨` 같은 문구를 사용한다.

## 9. 구현 순서

1. 셸 폭과 프로젝트 행 오버플로를 수정하고 축소 메뉴의 아이콘/tooltip을 복구한다.
2. 자산 화면을 로컬 탭으로 분리하고 `내 영상` 카드에 기존 썸네일·상태 projection을 연결한다.
3. 음악·효과음에 24개 페이지네이션을 적용하고 가져오기 카드 containment를 수정한다.
4. 편집기의 폭 정책, panel 내부 스크롤, timeline 스크롤 소유권을 수정한다.
5. 네 가지 PC viewport에서 실제 브라우저로 흐름과 시각 상태를 검증한다.

각 단계는 독립적으로 테스트하고 화면을 확인한 뒤 다음 단계로 넘어간다. 하나의 대규모 CSS 재작성으로 합치지 않는다.

## 10. 검증과 owner 완료 기준

완료는 테스트 통과가 아니라 owner가 실제 PC 화면에서 사용할 수 있는 상태다.

### 자동 검증

- 변경 컴포넌트의 focused Vitest
- 프런트엔드 전체 테스트
- typecheck 및 production build
- 홈·자산·편집기에서 `document.documentElement.scrollWidth <= window.innerWidth`
- 사이드바 자식의 bounding rect가 사이드바 rect를 벗어나지 않는지 확인
- 음악·효과음의 현재 DOM 카드가 페이지당 최대 24개인지 확인
- console critical error 0

백엔드 계약 변경은 의도하지 않는다. 예상 밖으로 백엔드 코드나 계약을 건드리게 되면 저장소 규정에 따라 `.venv/Scripts/python.exe -m pytest` 절대경로만 사용해 검증한다.

### 실제 브라우저 검증

다음 viewport에서 before/after screenshot을 남긴다.

- 1920×1080
- 1440×900
- 1366×768
- 1280×800

다음 실제 흐름을 마우스와 키보드로 확인한다.

1. 프로젝트 선택기 열기 및 프로젝트 전환
2. 홈에서 자산으로 이동
3. `내 영상`에서 영상 식별 및 상태 확인
4. 음악·효과음 탭 이동, 미리듣기 및 페이지 전환
5. 가져오기 탭에서 후보 식별
6. 편집기로 이동해 dock 전환, panel 스크롤, timeline 가로 스크롤 확인

### 화면별 합격 조건

- 사이드바 텍스트와 버튼이 겹치거나 sidebar 밖으로 나오지 않는다.
- 프로젝트 위험 작업이 실수로 노출되지 않고 더보기 메뉴를 통해 수행된다.
- 자산 화면에서 프로젝트 영상을 보기 위해 긴 라이브러리 목록을 먼저 통과하지 않는다.
- 영상 썸네일과 핵심 상태가 실제 데이터로 보인다.
- 음악·효과음 한 페이지가 24개를 넘지 않으며 문서 높이가 목록 전체 크기에 비례해 증가하지 않는다.
- 편집기 중앙 작업공간이 viewport 안에 있고 panel은 내부에서 스크롤한다.
- timeline 외의 문서 전체에는 가로 스크롤이 생기지 않는다.
- 1920px에서 양쪽 dock과 최소 720px preview가 보인다.
- 1280~1599px에서 한 dock만 보이고 다른 dock으로 전환할 수 있다.

모바일·태블릿 screenshot 및 모바일·태블릿 사람 검수는 이번 완료 기준에 포함하지 않는다. PC 화면의 owner 실제 사용 확인은 자동 검증과 별도의 최종 승인 gate로 남는다.

## 11. 외부 QA 문서의 선택적 반영

첨부된 `AK FINAL QA SYSTEM.md`의 모든 절차를 VideoBox에 그대로 이식하지 않는다. 현재 저장소의 운영 SSOT와 중복되거나, 인증·결제 등 이번 UI 복구와 무관한 범위가 포함되어 있기 때문이다.

다만 다음 원칙은 채택한다.

- 실제 브라우저 중심 검증
- 우선순위가 있는 결함 기록
- before/after 시각 증거
- 여러 PC viewport 확인
- 수정 후 동일 흐름 재검증
- 최소 변경과 회귀 확인

별도의 중복 SSOT인 `PROJECT_QA_MAP.md` 또는 `QA_REPORT.md`는 이번에 만들지 않는다. 구현 중 screenshot과 실행 증거는 기존 저장소 규칙에 맞는 단일 QA artifact 위치에 모으고, 최종 상태는 기존 handoff/status 체계에 기록한다.

## 12. 위험과 대응

- **기존 CSS 선택자와 새 sidebar 상태의 불일치**: 현재 DOM의 실제 `data-*` 상태를 기준으로 좁은 선택자를 사용하고 legacy selector에 의존하지 않는다.
- **자산 카드 로직 중복**: 편집기의 기존 asset projection과 thumbnail 계약을 우선 재사용한다.
- **페이지네이션으로 현재 선택이 사라짐**: 필터·페이지 전환 시 선택 상태를 검증하고 화면 밖 선택을 명시적으로 해제한다.
- **1280px에서 기능 발견성 저하**: 숨겨진 dock은 아이콘만 두지 않고 이름이 있는 PC 전환 제어를 제공한다.
- **CSS 수정의 전역 회귀**: 제품 셸, 자산 workspace, 편집기 workbench 경계별로 class를 제한하고 실제 브라우저 회귀를 단계마다 수행한다.

## 13. 승인 게이트

owner가 이 문서의 탭 구조, 데스크톱 폭 정책, 완료 기준을 승인한 뒤에만 파일 단위 구현 계획을 작성한다. 구현 계획 승인 전에는 production UI 코드를 변경하지 않는다.
