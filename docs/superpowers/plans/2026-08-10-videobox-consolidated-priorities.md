## 실행 0 — 한 번 편집하면 내보내기까지 갈 수 없다 — [x] 완료 2026-08-10 (owner 결정 2026-08-10)

**owner가 2안(단추)을 골랐다.** 편집할 때마다 자동으로 다시 만들지 않는다 — 편집은 자주
일어나고 검토는 마지막에 한 번 하는 일이라, 자동으로 하면 쓰지도 않을 계산을 계속 돌린다.

**한 일.** `refresh_review_for_current_edit`(저장소) + `POST
/api/projects/{id}/review-approvals/sessions/{session_id}/refresh` + 검토 화면의
`검토 다시 받기` 단추.

**합성을 다시 계산하지 않는다.** 출력 경로는 언제나 timeline과 session을 함께
materialize 하므로 timeline의 tracks는 손댈 것이 없다. 하는 일은 두 가지다 —
지금 편집본에서 **아직 비어 있는 장면만** 확인할 항목으로 다시 유도하고, 그 결과를
timeline과 승인 기록에 같은 revision으로 적는다.

**확인할 항목을 저장된 목록에서 베끼지 않는다.** 자산을 채운 장면은 override가 임시 클립
구간을 덮으므로 materialize 결과에서 사라진다. 베꼈으면 owner가 채운 뒤에도 "자산이
필요하다"가 남아서 영영 승인이 안 됐을 것이다.

**승인까지 대신 하지 않는다.** 상태는 `blocked` 또는 `draft`이고, `approved`로 올리는 것은
owner가 검토 화면에서 누를 일이다.

**컨테이너에서 owner 경로를 끝까지 밟았다.**

1. 자막을 고쳐 검토가 막히는 것을 재현 → `검토 다시 받기` → 검토 화면이 다시 열렸다
2. 빈 장면 2개에 자산을 적용(=편집) → `검토 다시 받기` → **"확인할 항목이 없어요"**
3. `검토 승인` → **"현재 편집본의 검토가 승인되었어요"**
4. `출력` 화면에서 **자막·완성본·CapCut 초안 세 단추가 모두 열렸다**

이 저장소에서 내보내기 관문이 열린 것은 이번이 처음이다.

**관문이 둘이었다.** 확인할 항목만 풀었더니 완성본이 400으로 막혔다 —
`assert_timeline_output_allowed`(`local_pipeline.py:2344`)는 확인할 항목이 아니라
`gap_slots`와 `placeholder_policy`를 보는데, 그것도 초안 때 적어 둔 값이라 owner가 다
채워도 그대로 남아 있었다. **같은 종류의 문제가 한 겹 아래 또 있었다.** 둘 다 materialize
결과에서 다시 유도하도록 고쳤다. 임시 클립은 렌더에 들어가지도 않는다 — 렌더도 session을
materialize 한 뒤 합성한다(`local_pipeline.py:1882`).

### 완성본이 실제로 나왔다 — [x] 2026-08-11

**이 저장소에서 mp4가 나온 것은 이번이 처음이다.**
1920×1080 h264 + aac, 15.0초, 2.5MB (`export_009`). 화면에도 재생기가 뜬다.

거기까지 가는 데 **낡은 표시 두 겹 말고도 문제가 둘 더 있었다.**

**(1) 적용한 자산이 없는 파일을 가리켰다.** 합성 계획 모듈은 저장소를 모르므로 세션
override에 경로가 없으면 `assets/{asset_id}`를 지어낸다(`composition_plan.py:468`).
그런데 자산은 종류별 폴더에 확장자를 달고 저장되므로 **그 경로는 언제나 존재하지
않는다.** `build_composition_plan`에서 저장소에 물어 채우도록 고쳤다 — 계획 모듈은
순수하게 두고, 이미 그렇게 저장된 편집본도 함께 복구된다.

**(2) ffmpeg가 스레드를 못 만들었다.** 진짜 오류는 잘린 stderr 뒤쪽이 아니라 앞쪽에
있었다 — `Error reinitializing filters!` 와 `-11 (Resource temporarily unavailable)`,
즉 **EAGAIN**이다.

| | 값 |
|---|---|
| `compose.yaml`의 `cpus` | **2.0** |
| 컨테이너 안 `nproc` | **16** (호스트 것이 그대로 보인다) |
| `pids_limit` | **128** |

ffmpeg는 `nproc`을 믿고 스레드를 잡는다. 입력 5개짜리 필터 그래프에 x264와 aac까지
붙으면 프로세스 상한을 넘고, 스레드 생성이 실패한다. 실측: 필터 스레드를 정하지 않으면
실패하고 2·4·8은 모두 성공한다. **인코더만 묶는 것으로는 부족했다 — 막힌 것은 인코더가
아니라 필터 쪽이었다.**

`cgroup`의 `cpu.max`를 읽어 **컨테이너가 실제로 받은 몫(2)** 을 기준으로 인코더와 필터
스레드를 함께 묶었다. 받은 것이 2개인데 16개를 띄우는 것은 빨라지지도 않으면서 상한만
먹는다.

**편집본 미리보기도 같은 원인이었다.** 스레드 상한을 둔 뒤 `미리보기 새로 만들기`가
성공하고, 편집기에서 실제로 재생된다(720×404). 두 경로가 같은 렌더러를 쓴다.

### (원본) 문제 설명

**owner 여정에서 가장 크게 막힌 곳이다. 오늘 브라우저에서 처음부터 끝까지 밟다가 찾았다.**

깨끗한 프로젝트로 앞뒤를 갈라 확인했다.

| | 검토 화면 | 검토 승인 단추 |
|---|---|---|
| 초안 직후(편집 0회) | 정상 — 장면 목록·확인할 항목이 보인다 | **있다** (확인할 항목이 남아 있어 비활성) |
| **자막 한 글자 고친 뒤** | **"이 검토본은 현재 편집본과 맞지 않아요"** | **사라진다** |

그 화면의 유일한 단추 `다시 확인`은 같은 것을 다시 불러올 뿐이라 **영원히 같은 답**이다.
`출력` 화면은 세 가지(자막·완성본·CapCut)를 전부 "검토 승인과 확인할 항목을 모두 마친 뒤"로
막는다. 즉 **편집을 한 번이라도 하면 그 프로젝트는 내보내기까지 갈 수 없다.**

**원인은 두 줄이다.**

- 편집이 일어나면 `_invalidate_output_freshness_with_connection`이 승인 기록을
  `is_current = 0`으로 내린다(`local_project_store.py:9851`, 이유 `editing_session_mutation`).
  **이 판단 자체는 옳다** — 옛 편집본을 검토한 결과로 새 편집본을 승인하면 안 된다.
- 그런데 승인 기록을 **새로 만드는 곳이 `materialize_atomic_draft_bundle` 한 곳뿐**이고
  (`:1988`, 항상 `source_session_revision = 1`), 초안을 만들 때 말고는 아무도 만들지 않는다.
  **내려놓기만 하고 다시 세우는 경로가 없다.**

**빠져나갈 수 없는 이유가 여기서 겹친다.** 빈 구간이 있는 초안은 `확인할 항목` 때문에 승인이
안 된다. 빈 구간을 채우려면 자산을 적용해야 하는데, **그 적용이 곧 편집이라 승인 기록이
죽는다.** 고치려면 편집해야 하고, 편집하면 못 고치게 된다.

**지금 통과할 수 있는 유일한 경우**는 처음 만든 초안이 빈 구간 없이 완벽해서 손댈 필요가
없을 때다. 그것이 "owner 최종 인수" 기록이 아직 없는 이유로 보인다.

**하는 일(제안).** 현재 편집본으로 검토본을 다시 만드는 경로를 만든다. 화면에 단추 하나를
더 다는 문제가 아니라, **편집 세션에서 timeline·검토본·승인 기록을 다시 세우는 일**이라
백엔드 작업이다. 어떤 모양이 맞는지(편집할 때마다 자동으로 다시 만들 것인가, owner가
"검토 다시 받기"를 누를 것인가)는 owner 결정이 필요하다.

**이번 세션에 고치지 않은 이유.** 30줄짜리 수정이 아니고, 동작을 정하는 데 owner 판단이
필요하다. 긴 세션 끝에 즉흥으로 넣을 변경이 아니다.

### 2-2. 미리보기 발행 중 예외가 렌더된 mp4를 지운다 — [x] 완료 2026-08-10

**계획과 다르게 처리했다. 코드가 맞고 아래 계획 문장이 틀렸다**(`local_project_store.py:904`).

## 고정 규칙 — 저장소는 Postgres 하나다 (owner 지시, 2026-08-10)

> "이제 앞으로 이 프로젝트에서 sqlite 는 안쓰고 모두 Postgres 이걸로 작업하도록만 해줘.
> db가 여러개면 관리가 안되잖아."

**적용 범위를 층으로 나눈다. 층마다 뜻과 비용이 다르다.**

| 층 | 지금 | 이 규칙이 요구하는 것 |
|---|---|---|
| 실행 중인 프로그램 | Postgres. 단 주소가 없으면 **조용히 SQLite로 떨어짐** | **폴백 제거.** 주소 없으면 뜨지 않는다 → P0-3 |
| 디스크에 남은 파일 | 런타임 폴더에 안 쓰는 SQLite 2벌 | 정리 → P0-3 |
| 테스트 | 73개 파일이 SQLite 임시 파일 사용 | **바꾸지 않는다** (아래 근거) |
| 코드 구조 | `PostgresProjectStore`가 `LocalProjectStore`를 **상속** | **바꾸지 않는다** (아래 근거) |

**테스트와 코드 구조를 바꾸지 않는 근거.** owner가 막으려는 위험은 "프로그램이 어느 DB를
보는지 모르는 것"이고, 그것은 위 두 층에서만 발생한다. 테스트가 쓰는 SQLite는 `tmp_path`에
만들었다 지우는 것이라 관리 대상 DB가 아니다. 그리고 **`LocalProjectStore`는 SQLite 구현이
아니라 저장소의 기반 클래스다** — 11,495줄의 로직이 전부 거기 있고 `PostgresProjectStore`는
연결과 메서드 6개만 갈아끼운다. 코드에서 SQLite를 들어내는 것은 저장소 전체 재작성이며,
owner가 겪는 문제를 하나도 해결하지 않는다.

**테스트가 SQLite만 본다는 위험은 별도로 이미 막았다** — `run-postgres-store-tests.ps1`.
더 나아가려면 73개 파일을 바꾸는 것이 아니라 **전체 회귀를 Postgres로도 돌릴 수 있게**
하는 쪽이 싸고 효과가 같다.

이름만 해시하고 잰다. 매번 폴더 전체를 다시 읽는 것은 이 저장소가 이미 한 번
치른 값이다.

**전제 하나를 확인했다 (2026-08-10) — 폴더에 넣는 것만으로는 부족하다.**
`index_pending_library_audio`는 폴더를 훑지 않는다. `library_audio_indexer.py:114`에서
**`store.list_assets_needing_audio_analysis(...)`로 라이브러리 DB를 읽는다.** 지금
그 DB를 채우는 것은 검증된 "팩" 설치뿐이다(`media_packs` 테이블).

그래서 남은 일은 폴더 감시 하나가 아니라 **둘**이다.

- 감시가 오디오 확장자를 받아 라이브러리 자리로 옮긴다 (촬영본 경로와 같은 모양)
- **옮긴 파일을 라이브러리 자산으로 등록한다** — 이게 없으면 파일은 들어가는데
  색인도 검색도 되지 않는다. 팩 설치가 등록하는 경로를 재사용할 수 있는지
  먼저 본다. 새 등록 경로를 만드는 것은 마지막 수단이다.

**이 전제를 확인하지 않고 폴더 감시만 붙였으면** 파일은 옮겨지는데 검색에 안 잡혀서,
owner에게는 "넣었는데 안 된다"로 보였을 것이다 — 오늘 고친 침묵과 같은 모양이다.

**검증 — 컨테이너에서 실제로 확인했다 (2026-08-10).** 재빌드·재기동 뒤 `새 음악`에
mp3를, `새 효과음`에 wav를 넣었다.

- 감시 한 바퀴가 지나자 두 폴더가 비었고 원본 둘 다 `자산화_완료`에 모였다
- 라이브러리 자리에서 종류대로 갈라졌다 (`owner-audio/music`, `owner-audio/sfx`)
- 로그: `직접 넣은 소리 2개를 라이브러리에 넣었습니다.`
- `/api/media-library/assets`에 `verified: true`로 나온다. 길이는 ffprobe가 잰
  실제 값(8.05초, 0.4초), 종류는 들어온 폴더대로 `music`/`sfx`. 팩 자산 130개는
  그대로 살아 있다(합계 132개)
- 색인기가 알아서 재고 문장을 붙이고 벡터까지 만들었다
  (`아주 짧게 한 번 스치는 효과음. …`, `description_version=2`)
- `/api/media-library/search`가 실제로 돌려준다 — 효과음 질의에서 팩 130개와
  같이 겨뤄 50개 중 29위(0.897)
- 미리 듣기도 200 `audio/mpeg`로 나온다
- 4분 넘게 두고 봐도 등록 로그는 한 줄뿐이다. 할 일이 없는 바퀴는 값이 안 든다
