# 배선을 한 겹 더 갔다 — 소리 크기가 드디어 파일에 닿는다

- 작성: 2026-08-18 (밤 세션 마감, 앞 세션 이어서)
- **읽는 순서:** 이 문서 →
  `docs/handoffs/2026-08-18-videobox-speed-volume-ducking-and-transport.ko.md`
  (배속·음량 배선, 덕킹 토글, 스페이스·전체 보기)

## 왜 또 같은 자리를 팠나

앞 세션에서 `소리 크기`를 렌더러까지 이어 놓고 "됐다"고 보고했다. **틀렸다.**

owner가 "완성본 하나 뽑아 달라"고 해서 실제로 뽑아 보는 김에 배선을 다시 훑었더니,
음량은 **여전히 결과에 닿지 못하고 있었다.** 한 겹 앞이 비어 있었기 때문이다.

B-roll 음량은 그 클립의 **자체 소리를 살려 둘 때만** 섞인다
(`preserve_source_audio`). 그런데:

- 그걸 켜는 스위치가 화면에 **없었다**
- 백엔드에서도 이 값을 참으로 만드는 곳이 **한 군데도 없었다** — 읽기만 했다

즉 B-roll 소리는 언제나 꺼진 상태였고, 음량을 아무리 조절해도 섞일 소리가 없었다.
**앞 세션에서 내가 "음량이 이어졌다"고 한 것은 렌더러 안쪽까지만 맞는 말이었다.**

## 이번에 고친 것 둘

### 1. `이 영상의 원래 소리도 함께 쓰기` 스위치

`소리 크기` **바로 아래**에 뒀다. 둘은 한 벌이라 떨어뜨려 놓으면 관계가 안 보인다.

### 2. 저장 경로가 네 값을 흘리고 있었다

`editorCommandPort`의 `mediaControls()`가 **정해진 키만** 실어 보냈다. 서버는 안 온
키를 기본값으로 되돌리므로, **인스펙터에서 배속만 고쳐 저장해도**
`preserve_source_audio`·`loop`·`pad`·`trim_start_sec` 네 값이 초기화됐다.

지금 데이터가 전부 기본값이라 실제 손실은 아직 없었다. 하지만 누가 그중 하나를
기본이 아닌 값으로 만드는 순간 조용히 사라졌을 것이다.

**교훈: 새 제어를 만들면 화면에 붙이는 것으로 절반이다.** 저장 경로 목록에도
넣어야 한다. 그 목록은 `editorCommandPort.ts`의 `mediaControls()` 하나다.

### 3. 그리고 진짜 큰 것 — B-roll 저장 단추가 잠겨 있었다

스위치를 붙이고 화면에서 눌러 봤는데 **서버가 안 바뀌었다.** 원인:

저장 단추가 `쓸 구간 끝 <= 시작`이면 잠기게 돼 있었는데, **구간을 정하지 않은
B-roll은 시작·끝이 둘 다 0**이라 이 조건에 걸린다. 즉 구간을 따로 지정하지 않은
평범한 클립은 **배속·음량·페이드·소리 스위치 어느 것도 저장할 수 없었다.**

`0/0`은 잘못된 구간이 아니라 **구간을 안 정했다**는 뜻이다. 이제 그때는 구간을
아예 보내지 않는다(서버가 `끝 > 시작`을 요구하므로 0/0을 보내면 거절당한다).
끝이 시작보다 진짜 앞이면 여전히 막는다.

**같은 자리에서 하나 더 나왔다.** 페이드와 구간이 하나의 삼항으로 묶여 있어서,
구간을 가진 B-roll은 페이드를 고쳐도 **옛 값이 실려 나갔다.** 둘을 따로 판단하게
나눴다.

### 내가 어제 잘못 보고한 이유

**화면에 남은 값을 서버에 저장된 값으로 착각했다.** 저장이 실패해도 입력칸의
로컬 상태는 그대로 남는다. 그래서 "배속 2배가 저장돼 되돌아왔다"고 보고했는데,
실제로는 서버에 가지 않았다(그때 완성본이 나온 건 내가 따로 API를 직접 호출해
값을 넣었기 때문이다).

**저장을 확인할 때는 화면이 아니라 서버 응답을 봐라.** 세션을 다시 읽어
`session_revision`이 올라갔는지, 그 값이 실제로 들어갔는지 확인한다.

### 4. 소리를 켰더니 영상 전체가 조용해졌다 (`amix` 정규화)

owner가 "소리 살린 완성본"을 요청해 뽑아 보니, **B-roll 소리를 켠 순간 그 장면과
아무 상관 없는 구간의 내레이션까지 작아졌다.** 완성본을 2초 간격으로 재서 찾았다.

`amix`는 기본으로 **입력 수만큼 나눈다**(`normalize=1`). 소리를 하나 더하면
이미 있던 소리가 전부 절반이 된다. 켠 사람은 소리를 **더한** 것이지 나머지를
줄인 게 아니다. 두 곳 모두 `normalize=0`으로 고쳤다.

**두 곳이다 — 이게 핵심이다.** 처음에 `render_timeline_to_mp4`의 믹스(1091행)만
고치고 재빌드했는데 **결과가 그대로였다.** 실제 완성본은
`build_plan_audio_filter_graph`(414행)를 타기 때문이다. 배속 때와 **똑같은 함정**에
두 번째로 걸렸다.

> **렌더 경로가 둘이다.** `_extract_segment`+concat 경로와 합성 계획 그래프 경로.
> 오디오·비디오 무엇을 고치든 **두 곳을 같이 본다.** 한 곳만 고치고 테스트가
> 초록이면 그 테스트가 다른 경로를 타고 있는 것이다.

고친 뒤 재서 확인: 모든 구간에서 소리가 **커졌다**(예: 16초 지점 -22.0 → -16.1dB).

**배경 음악·효과음 믹스도 같은 방식으로 정규화한다.** 그건 오래된 동작이라
바꾸면 지금까지 뽑은 모든 완성본의 소리 균형이 달라진다 — owner 결정 사항으로
남긴다. 이번에 고친 것은 **오늘 처음 켤 수 있게 된 경로**뿐이라 기존 출력은
그대로다.

**덤으로 찾은 잠복 결함:** 배경 음악 믹스 단계가 입력으로 `audio_path`가 아니라
`narration_path`를 다시 쓴다(1125행). 배경 음악이 있는 프로젝트에서는 B-roll
소리 믹스가 통째로 버려진다. 이번 타임라인에는 음악 트랙이 없어 드러나지 않았고,
고치지 않고 남겨 둔다 — 고치면 음악 있는 기존 프로젝트의 소리가 달라진다.

## 완성본을 실제로 뽑아 보고 알게 된 것

owner 요청으로 `My Project`에서 배속 2배 완성본을 뽑았다(`export_009`). 그 과정에서:

- **처음 고른 장면으로는 배속이 보이지 않았다.** 그 장면이 쓰는 B-roll이 4초짜리
  영상인데 **120프레임이 전부 같은 그림**이었다. 정지 화면을 빨리 돌려도 같은
  정지 화면이다. 코드 문제가 아니었다.
- 실제 촬영본(494초)을 쓰는 장면으로 옮겨 다시 뽑고, **1배속본을 하나 더 뽑아
  A/B로 비교**했다. 배속 건 구간은 네 지점 모두 다르고, 안 건 구간은 완전히 같다.

**배속을 시험할 때는 움직임이 있는 촬영본을 골라라.** 이 프로젝트의 짧은 B-roll은
정지 영상이라 아무것도 증명하지 못한다.

## 검증

- 백엔드 80개 통과. 신규 `test_broll_volume_actually_changes_how_loud_the_finished_file_is`는
  **실제 파일의 음량을 잰다** — 소리를 살리고 4분의 1로 줄이면 측정 음량이 실제로
  낮아진다. 길이가 아니라 음량으로 재는 규칙을 지켰다.
- 웹 1,074개 통과, `tsc --noEmit` 깨끗, e2e 48개 통과(스냅샷 포함)
- **컨테이너 재빌드 후 실제 화면 → 서버까지 확인:** 소리 스위치를 켜고 음량을
  0.5로 저장하니 세션이 revision 38로 오르고 `preserve_source_audio: true`,
  `volume: 0.5`가 실제로 들어갔다. 확인 뒤 기본값으로 되돌렸다(revision 39).

## owner 프로젝트 상태

검증하느라 `My Project`에 넣었던 값(배속 2배, 음량 0.8)은 **전부 원래대로 되돌렸다.**
현재 장면 7개 모두 기본값이다. 세션의 `history`에는 그 흔적이 남아 있는데 그건
되돌리기 이력이라 정상이다.

다만 **검토 승인은 새로 되어 있고 완성본이 세 개 늘었다**(`export_007`~`009`).
지울 필요는 없지만 owner가 목록에서 볼 것이므로 적어 둔다.

## 남은 사람 확인

- **미리보기 전체화면 실제 진입** (앞 세션에서 계속 넘어옴). 브라우저가 실제 마우스
  클릭에서만 허용해서 자동 확인으로는 단추 렌더·상태 동기화까지만 봤다.
- **소리를 살린 B-roll을 실제로 들어 보기.** 자동 검증은 "더 조용해졌다"까지고,
  말소리와 섞였을 때 듣기 좋은지는 사람 몫이다.
