# 프롬프트 수정 부작용 실물 스윕, 오류 문구 누출 수정도 실물로 확인됨 (2026-09-13 낮)

앞 인계(`2026-09-13-short-form-chat-and-render-done-reply-text-root-cause-found.
ko.md`)가 새벽에 남긴 "다음 세션이 먼저 할 일" 4개 중, 대표님이 사무실
데스크톱에서만 확인 가능한 캡컷 R2와 급하지 않다고 확인된 R1
(`task_006f1523`)을 제외하고, 이번 세션엔 3번과 4번을 실물로 확인했다.
코드는 고치지 않았다 — 새로 발견한 문제 하나는 owner 판단이 필요해 큐에
올렸다(`task_77685434`).

## 1. 4번 — 편집기 채팅 내부 오류 문구 누출 수정, 실물(브라우저)로 확인됨

앞 인계는 "LM Studio를 일부러 내려야 재현할 수 있는데 다른 프로젝트와 GPU를
공유해서 이번 세션 범위를 벗어난다"고 남겼다. 이번 세션엔 **일부러 내리지
않고도** 실물 확인 기회가 생겼다: 실제 웹 화면에서 "사진 브이로그 실기
0907" 프로젝트의 편집기 채팅에 연달아 메시지를 보내다가, 로컬 모델이
실제로 `Local Qwen request timed out.`을 던지는 상황이 자연스럽게 발생했다.

네트워크 탭으로 실제 응답을 확인하니 백엔드는 여전히 원본 예외를 그대로
담아 보낸다(`"text": "local_only_blocked: local_qwen: Local Qwen request
timed out."`, `metadata.error_code: "LOCAL_TIMEOUT"`) — 이건 의도된 동작이고
프론트가 걸러야 한다. 그런데 실제 화면에는 원본 문자열이 아니라 **"유진의
답을 받지 못했어요."**만 떴다 — `EditorWorkbenchRoute.tsx`의
`localizeDirectorAssistantText`(커밋 `f07ebf43`)가 `"local_only_blocked:
"` 접두사를 실제로 걸러내고 있다는 뜻이다.

**결론: 4번 항목은 실물로 검증 완료. LM Studio를 내릴 필요 없이 자연 발생한
타임아웃으로 충분히 확인됐다.**

## 2. 3번 — 프롬프트 수정 부작용 스윕, 진짜 문제 하나 찾음

`tests/test_yujin_local_conversation_live_smoke.py`와 같은 방식(LM Studio에
실제로 로드된 모델을 자동 탐지해서 진짜로 호출, 가짜 provider 없음)으로
`YujinLocalConversationService.reply()`를 여러 시나리오에 직접 태워봤다.

**정상 확인된 것:**
- "지금 화면에 뜬 추천 자료 카드 적용해줘"(카드/추천 단어 포함) →
  "그 후보는... 카드에서 적용 단추만 누르면 바로 붙일게요" — 카드는 직접
  클릭이 필요하다는 구분을 정확히 지켰다.
- "그 후보 적용해줘"도 동일하게 정확했다.
- "1번 장면 속도를 두 배로 빠르게 해줘"(직접 편집 의도) → "네, ...바로
  화면에 반영되어 있어요" — 새벽 수정이 의도한 대로 정확했다.
- "이 장면에 어울리는 B-roll을 추천한 이유가 뭐야?"(일반 질문) → 정보가
  없다며 되묻는 정상 답변, 회귀 없음.

**문제를 찾았다 (3/3 재현, owner 판단 필요해 `task_77685434`로 큐에 올림):**
"응 그걸로 적용해줘"처럼 **번호나 카드/후보 같은 단어 없이 순수하게
확인만 하는 문장**을 3번 반복 테스트했더니 **매번** "네, 바로
적용했어요"/"자동 반영 중입니다"처럼 이미 적용됐다고 답했다.

문제는 이게 실제로 화면에 떠 있는 게 **자료 추천 카드**인 상황이면 거짓
긍정이라는 점이다 — 카드는 여전히 사람이 직접 "적용" 버튼을 눌러야
붙는다. 코드를 추적해 보니 원인 경로가 실재한다:
`director_commands.py`의 `resolve_director_command()`는 문장에 숫자나
참조 코드(`1번`, `B-01` 등)가 없으면 무조건 `"unresolved"`를 반환하고,
그러면 `routers/director_proposals.py`가 blind LLM(이번에 고친 그
프롬프트)으로 폴백한다. "그걸로"에는 숫자가 없으니 정확히 이 경로를 탄다.

게다가 `EditorWorkbenchRoute.tsx`의 `interpretAndApplySpokenEdit`
주석(2138줄)이 확인해 주듯, 이렇게 애매한 문장은 별도의 분류·적용 경로
(`createYujinEditingProposal`)에서도 유효한 편집 의도로 안 잡힐 가능성이
높다 — 즉 **실제로는 아무 일도 안 일어났는데 채팅 답변만 "적용했다"고
말하는 상황**이 실제로 생길 수 있다는 뜻이다(적용 경로 자체를 실물로
재현하지는 않았다 — 반례 가능성 있음, 아래 "남은 것" 참고).

**이번 세션엔 안 고쳤다.** 이 프롬프트는 2026-09-01 결정과 오늘 새벽 수정
(`a349539c`)이 막 확정한 것이라, 세 가지 방향(결정론적 리졸버 확장 / 프롬프트에
불확실성 되묻기 문구 추가 / 그대로 둠) 중 어느 쪽이 그 결정의 취지에 맞는지는
대표님 판단이 필요하다고 봤다. 상세 재현 방법과 세 방향은 `task_77685434`에
그대로 적어 뒀다.

## 3. 남은 것

- `task_77685434`의 실제 화면 영향(애매한 확인이 정말 화면에 아무 변화 없이
  "적용했다"는 문구만 남기는지)은 **아직 채팅 답변 레이어에서만** 확인했다 —
  `createYujinEditingProposal` 분류기가 실제로 그런 문장을 어떻게 처리하는지는
  코드 추적만 했고 실물로는 안 밟았다. 다음에 이 task를 열면 그 확인부터
  하는 게 좋다.
- `task_006f1523`(R1 경계 나누기), CapCut R2(세로 블러 육안 확인)는 여전히
  대기 중 — 전자는 급하지 않음 확인됨, 후자는 대표님이 사무실 데스크톱에서
  직접 봐야 한다.
