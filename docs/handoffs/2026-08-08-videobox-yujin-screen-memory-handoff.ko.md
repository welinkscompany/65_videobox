# 2026-08-08 세션 핸드오프 — 승인한 기억이 처음으로 화면에서 쓰이기 시작한 날

## 한 줄 요약

유진의 기억 조회는 **한 번도 동작한 적이 없었다.** 게이트웨이 두 겹이 어댑터의 정상
응답을 해석하지 못했고, 실패 사유는 통째로 삼켜져 "기억 없음"으로만 보였다. 그걸 고친
뒤에도 owner 화면에서는 여전히 쓸 수 없었다 — **조회가 화면이 쓰지 않는 경로에만
붙어 있었기 때문이다.** 네 겹을 다 뚫고 나서야 편집 화면에서 한 바퀴가 돌았다.

## 지금 어디까지 되나 (화면 실측)

편집 화면에서 실제로 눌러서 확인했다. **헤르메스는 한 번도 쓰지 않았다.**

```
나   내 자막 배치 취향이 어떻게 되는지 숫자까지 그대로 알려 주세요.
유진 자막은 화면 아래에서 27% 지점에 배치합니다.
```

`27%`는 대화에 한 번도 등장한 적이 없고, 같은 화면의 `기억` 칸에 적어
`승인하고 저장`한 문장에만 있던 숫자다. 시험용 기억 두 개는 화면에서 지웠다.

## 막고 있던 것 넷 — 하나 고칠 때마다 다음 게 나왔다

### 1. 게이트웨이가 자기 어댑터의 답을 못 읽었다 (두 겹)

응답 모델이 `strict=True`인데 `memories`가 `tuple`이다. JSON은 언제나 배열(`list`)로
오고, strict 파이썬 모드는 list를 tuple로 받아주지 않는다. 매번 검증 예외 → 503 →
위층이 예외를 삼키고 빈 결과. **어댑터는 내내 정상이었다** — 200에 기억까지 담아
돌려주고 있었다.

- `memory_gateway.py`의 `HermesMemoryAdapterClient.search` (게이트웨이 → 어댑터)
- `agent_gateway_client.py`의 `search_memory` (API → 게이트웨이)

둘 다 이미 읽어둔 응답 **바이트**를 `model_validate_json`으로 해석하게 바꿨다.
`.json()`을 거치면 dict/list가 되어 strict 모드에 걸린다.

**테스트가 못 잡은 이유는 늘 같은 그것이다.** 검색 테스트가 전부 파이썬 객체를 그대로
돌려주는 가짜 어댑터를 썼다. HTTP JSON을 거치는 검색 테스트가 **한 개도 없었다.**

### 2. 화면 채팅 경로가 기억을 읽지 않았다

기억 조회는 `hermes_run_service`에만 배선돼 있었고, **`api.ts`의 `createHermesRun`을
부르는 화면이 없다.** 편집 화면의 `요청 보내기`는 로컬 우선 경로(`/messages`)로 간다
(owner 결정 `2026-08-05-local-first-assistant-decision.ko.md`).

`director_proposals.py`의 로컬 분기에서 `retrieve_approved_memories`를 부르고,
`YujinLocalConversationService.reply(memories=...)`가 프롬프트에 싣게 했다. 기억이
없으면 절 자체를 넣지 않는다 — 빈 제목은 모델이 취향을 지어내게 만든다.

### 3. 화면에서 나눈 대화로는 기억을 만들 수 없었다

`_completed_yujin_memory_source_rows`가 **완료된 헤르메스 run에 속한 메시지만**
기억의 재료로 인정했다. 로컬 경로에는 run 객체 자체가 없다(설계상 그렇다). 그래서
owner는 실제로 나눈 대화로 기억을 만들 수가 없었다.

완료된 로컬 턴 — `append_director_exchange`가 쓴 요청/응답 쌍 — 도 재료로 인정하게
넓혔다. **막을 것은 그대로 막았다:**

- 그냥 `append_director_message`로 들어온 메시지는 여전히 제외(`client_message_id`가 없다)
- 실패한 답변(`status: blocked`)도 제외 — 읽지 못한 메타데이터는 실패로 친다
- **어떤 run이든 소유한 메시지는 이 분기로 오지 않는다.** 안 그러면 진행 중이거나
  막힌 run이 "두 줄이 나란히 있다"는 이유만으로 통과한다

### 4. 그래도 버튼이 안 눌렸다 — 화면에 규칙이 한 벌 더 있었다

`EditorWorkbenchRoute.tsx`의 `completedDurableMemoryMessageIds`가 `hermes_run_id`를
요구하고 있었다. 서버 규칙과 같은 모양으로 맞췄다.

**교훈: 같은 규칙이 서버와 화면에 각각 있으면 한쪽만 고쳐도 사용자에게는 아무것도
바뀌지 않는다.**

## 컨테이너에서 유진 대화가 아예 안 되던 것도 함께 고쳤다

화면에 뜨던 문구: `local_qwen: Local Qwen request failed due to a transient network error`

`settings.py`가 로컬 모델 주소를 `http://127.0.0.1:1234/v1`로 **못박고 다른 값을
거부**하고 있었다. 컨테이너 안에서 `127.0.0.1`은 컨테이너 자신이고 LM Studio는
호스트에 있다. **컨테이너 모드에서는 구조적으로 두뇌에 닿을 수 없었다.**

`VIDEOBOX_LOCAL_RUNTIME_BASE_URL`을 두고 `host.docker.internal:1234` **하나만** 추가로
허용한다. 그 이름은 도커 호스트 — 같은 기계 — 를 가리키므로 "이 컴퓨터 밖으로 나가지
않는다"는 보장은 그대로다. owner 승인 2026-08-08, `§10.14` 조항 2-B에 기록했다.

## 알아둘 것

**기억은 대화 단위로 갇혀 있다.** 조회 SQL이 `WHERE conversation_id = ?`다. 다른
대화에서 승인한 기억은 설계상 절대 나오지 않는다. 앞선 인계의 "새 대화에서 확인하라"는
절차는 아무리 해도 통과할 수 없다. 넓힐지는 별도 결정이다.

**유진은 기억 후보를 제안하지 않는다.** `videobox-memory/SKILL.md`가 "대화 내용을 자동
수집·저장하지 않는다"고 못박고 있고, owner가 `기억` 칸에 직접 적는 것이 의도된 설계다.
앞선 인계의 "후보 제안 흐름 확인" 항목은 전제가 틀렸다.

**컨테이너를 다시 빌드하면 브라우저가 옛 번들을 잡고 있다.** 화면이 이상하면
제품 결함으로 보기 전에 주소창에 아무 쿼리나 붙여 강제로 다시 받아 본다. 이번에
`유진 기억` 패널이 통째로 사라진 것처럼 보였는데 원인이 이것이었다.

## 홈 대시보드도 실제 상태를 말하게 했다 (Task 35 완료)

owner가 "대시보드가 전부 완성돼야 테스트할 수 있다"고 해서 이어서 진행했다. 홈은
카드 세 개의 문구를 **전부 무조건 단정**하고 있어서 셋 다 거짓일 수 있었다 —

**막고 있던 제약을 뒤집지 않고 우회했다.** `ProductShell.test.tsx`가 "작업 목록은

세지 못하는 홈이 이동까지 막아서는 안 된다.

브라우저 실측으로 하드코딩이 아님을 확인했다 — `b-roll-smoke-test`는
