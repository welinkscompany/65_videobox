## 한 줄

owner가 세 항목(Hermes 실제 로그인, MCP 착수, 자유 멀티트랙)을 모두 승인했다.
MCP는 첫 슬라이스(프로젝트 넷 + job_status)를 실제로 짓고 살아 있는 컨테이너에
대고 검증까지 끝냈다(커밋 `555a26a69`, main에 병합·push 완료). Hermes egress
게이트웨이와 자유 멀티트랙은 코드가 아니라 **검토 가능한 단계별 계획**부터
뽑았다 — 둘 다 보안·아키텍처 영향이 커서, 이 세션에서 "작다고 판단했다가
회귀를 낸" 경험([[videobox-2026-09-08-transcription-async-regression]] 참고할
메모는 아직 없음, 본문 §1-6 참고) 뒤라 계획 없이 코드부터 쓰지 않기로 했다.

**추가로 owner가 "기억 사서"(대화를 훑어 기억 후보를 자동으로 만드는 것)를
요청해 첫 슬라이스를 완료했다(§6) — mem0 9번 중복 저장 버그 수정, 정형구
필터, 워터마크, 증류 진입점, owner 수동 실행 스크립트까지 커밋 넷, **실제
LM Studio로 관통 검증**(진짜 대화 → 진짜 distilled 후보가 승인 대기로
쌓임)까지 끝났다. 자동 스케줄링은 아직 없다(owner가 수동 실행).

## 2. Hermes egress 게이트웨이 계획 — owner 결정 대기 항목 여섯

`docs/implementation-plan.ko.md` §23.1·§23.2.6·§23.4·§23.6을 6단계로 짠
계획(Plan 에이전트 산출, 코드 없음). **로그인 자체(`hermes auth add
openai-codex --type oauth`)는 어느 단계에서도 자동화하지 않는다** — owner가
직접 치는 절차로 그대로 둔다.

### 단계 요약

| 단계 | 내용 | 크기 | 막힘 |
|---|---|---|---|
| 1 | 허용목록 판정 로직(순수 함수, 소켓 없음) | 소 | 호스트 이름 목록(결정 2) |
| 2 | TLS SNI 패스스루 프록시(실제 소켓 시험) | 중~대 | 프록시 기술(결정 1) |
| 3 | compose 네트워크를 `internal: true`로 전환 + 프록시 배선 | 중 | **owner 승인 필요**(CLAUDE.md §6), Hermes가 proxy 환경변수를 실제로 따르는지(결정 4) |
| 4 | 서명 키 회전 + owner 승인 revoke 문(저장 로직은 이미 있음, 부르는 자리만 없음) | 중 | 없음 — 바로 시작 가능 |
| 5 | 실제 GPT 호출 앞 동의·예산 게이트 | 대 (가장 큼) | 예산 단위·상한(결정 6) |
| 6 | fail-closed 인수 시험 일곱 가지 | 대 | 앞 단계 전부 |

### owner 결정 필요한 여섯 가지

1. **프록시 기술** — 직접 짠 Python SNI 프록시 vs 기성 Squid. 계획은 전자를
   권장(이 저장소 스타일과 맞고 pytest로 검증 가능) — 승인/변경 여부.
2. **정확한 OpenAI 허용 호스트 이름 목록** — 저장소 어디에도 확정된 목록이
   없음. Hermes 공식 배포판 문서에서 찾거나, "관찰만 하는" 임시 감사 모드로
   실제 로그인 한 번 돌려 본 뒤 확정하는 두 경로 제안.
3. **Mem0 egress와 OpenAI egress를 같은 네트워크·허용목록으로 묶을지, 나눌지.**
4. **Hermes가 `HTTPS_PROXY`류 환경변수를 실제로 따르는가** — 공식 배포판
   소스·문서에서 확인 필요(3단계 착수 전 필수).
5. **새 게이트웨이 서비스 코드 위치** — `services/egress-gateway/` 신설(권장)
   vs 기존 `agent-gateway` 안에 추가.
6. **예산 게이트의 단위·상한** — 토큰 수/비용/요청 수, 상한 값.

**바로 시작 가능한 것**: 1단계(허용목록 판정 로직, 실제 호스트 이름은 나중에
끼워 넣어도 되는 구조)와 4단계(키 회전·revoke 문 — 결정 사항 없음, 저장
로직은 이미 시험까지 있고 부르는 자리만 없다).

## 3. 자유 멀티트랙 계획 — owner 결정 대기 항목 넷

7단계(Plan 에이전트 산출, 코드 없음). 핵심 설계 결정과 근거:

**"6개 역할"은 사실 파일마다 다른 다섯 개의 서로 안 맞는 집합이었다**
(`canonical_track.py` 4개, `track_states.py` 6개, `composition_plan.py` 5개,
`editing_session.py` 5개, CapCut adapter 4개) — 이미 숨은 불일치 버그다.

**세그먼트가 트랙 중심이 아니라 "내레이션 세그먼트에 달린 필드"** 구조라
(`broll_override`처럼) 트랙을 자유화하려면 클립 배치를 세그먼트 정체성에서
떼어내야 한다 — 단순 enum 완화가 아니다.

**타이밍 기준(내레이션이 여럿이면 뭐가 기준?) 설계**: `is_timing_anchor`
플래그(내레이션 트랙 하나만 true) + 자막 트랙의 `source_track_id`(어느
내레이션을 옮기는지) 권장. 완전 분리형(트랙 개념 자체를 없애고 프로젝트
수준 컷 리스트로) 대안도 검토했으나 이번 범위엔 너무 큼 — 다음 단계로 남김.

두 승인 문서(`2026-07-20-editor-workbench-visual-approval`,
`2026-08-30-capcut-button-level-parity`) 재확인 결과 **6줄 고정을 별도로
승인한 문서가 아니다** — 재승인 없이 진행 가능.

### 단계 요약

| 단계 | 내용 | 결정 필요 |
|---|---|---|
| 0 | 다섯 집합 정리 -- **아래 정정 참고, "즉시 착수 가능"이 아니다** | 재조사 필요 |
| 1 | 백엔드 트랙 레지스트리 스키마 + 옛 세션 마이그레이션 -- **완료**(`d0429239`) | 마이그레이션이 자동인지 확인창을 띄울지 |
| 2 | B-roll/음악/효과음 클립 배치를 세그먼트에서 분리 -- **완료**(§8) | 없음 |
| 3 | 타이밍 기준·자막 출처 일반화 | 기준 트랙 삭제 시 동작(막기/다른 트랙 지정/그대로 얼림) |
| 4 | ffmpeg 렌더러 일반화(가장 큰 단일 파일 변경) | 없음 |
| 5 | 트랙 추가/삭제/순서 API | 추가·삭제 UX 형태, 개수 제한 |
| 6 | CapCut 내보내기 일반화 | 없음 |
| 7 | 프런트(타임라인 UI, 추가/삭제/기준 표시) | 3·5의 결정에 종속 |

**바로 시작 가능한 것**: 1·2·4·6단계(엔진·내보내기 쪽은 owner 결정 없이도
설계대로 진행 가능 — 결정이 필요한 건 5단계의 삭제 가드레일·추가 UX뿐).

**"0단계" 정정 (같은 세션, 이어서 직접 확인함)** — 계획을 세운 서브에이전트는
다섯 집합을 "그냥 불일치, 하나로 합치면 되는 버그"로 판단했는데, 직접
사용처를 추적해 보니 **적어도 둘은 서로 다른 목적으로 일부러 다른 것**이었다:
- `track_states.TRACK_STATE_KINDS`(6개, 자막·오버레이 포함)는 "숨김/음소거
  단추가 뜻이 있는 트랙 종류" — `VALID_CANONICAL_TRACK_TYPES`(4개)는
  "`timeline.tracks` 안에서 `segment_id`로 순서를 되짚을 수 있는 트랙 종류"
  (`_pipeline_private_helpers.py:603`). 이 둘을 하나로 합치면 오히려 자막·
  오버레이가 세그먼트 순서 재구성 로직에 잘못 끼어들 위험이 있다.
- `composition_plan._SUPPORTED_TRACKS`·`editing_session.FIXED_TIMELINE_TRACK_ROLES`는
  이미 서로 같다(둘 다 5개, overlay 포함). CapCut의
  `VALID_EXPORT_TRACK_TYPES`(4개)는 `VALID_CANONICAL_TRACK_TYPES`와 이미
  같다 — overlay를 CapCut이 따로 처리하기 때문으로 보인다.

**진짜 있을 수 있는 갭 하나만 좁혀서 남긴다 → 확인 완료, 결함 아님(2026-09-08,
같은 세션 자율 점검에서 마저 확인)**: `_pipeline_private_helpers.py:603`이
4개짜리 집합을 써서 overlay 트랙의 클립을 순서 재구성에서 건너뛰는데,
`composition_plan.py:603,607`에서 확인한 대로 overlay 클립도 실제로
`segment_id`를 갖는다 -- 하지만 이 함수의 용도는 "이미 다 아는 세그먼트의
순서를 매기는 것"이지 "세그먼트를 새로 찾는 것"이 아니고, 오버레이가 있는
세그먼트는 정의상 내레이션/B-roll 클립도 이미 갖고 있어(오버레이는 세그먼트
위에 얹는 부가물이지 단독으로 존재하지 않는다) 그쪽에서 이미 순서에
잡힌다. **관찰 가능한 결함으로 이어지지 않는다** -- 다섯 집합은 그대로
둔다. 다음에 이 자리를 또 열 필요는 없다.

### owner 결정 필요한 네 가지

1. 타이밍 기준 내레이션 트랙을 지우면: (a) 못 지우게 막기 (b) 다른 트랙을
   먼저 기준으로 지정해야 지울 수 있게 (c) 지우고 세그먼트 타이밍은 그
   순간 값으로 얼리기. 계획은 (a)+(b)를 기본값으로 권장.
2. 자막 트랙이 가리키던 내레이션 트랙을 지우면: 자막도 같이 지우기 / 기준
   트랙으로 재배정 / 재배정 전엔 삭제 막기.
3. 옛 프로젝트(고정 6트랙)를 열 때 새 구조로 **조용히** 바꿀지, "전환할까요?"
   확인창을 띄울지.
4. 트랙 추가/삭제 화면 조작 방식, 트랙 개수 상한 여부.

### 6.0 VideoBox 실측 (착수 전 측정, 결정과 무관하게 유용한 발견)

- **mem0 저장 상태**: 정상 동작(임베딩 실제로 쓰임, 차원 일치). 다만 한 달간
  서로 다른 기억 3건뿐이고, 그중 하나("배경음악은 목소리 안 덮게")가 **9번
  중복 저장**돼 있었다 — 원인은 `infer=False`(owner 원문 재해석 방지, 그대로
  둠) + 상위 dedup 부재. **이 세션에서 고쳤다**(§ 아래, mem0 저장 전 정확히
  같은 문장 검색 후 있으면 재사용).
- **대화 기록**: Postgres `director_messages`에 184건, 개발 세션에 몰림.
  **시스템 프롬프트 전체가 로그에 안 섞인다**(user_text/assistant_text만
  저장) — Rumi가 겪은 문제보다 범위가 좁다. 다만 `director_proposals.py`의
  고정 응답("어느 참조인지 선택해주세요." 등)은 반복되므로 정형구 필터가

**조사에서 알아낸 것**: 이 두 엔드포인트는 순수 분석 API다(구간을 찾아

`raw_video_asset_id`(프로젝트 자산 표)라서 "촬영본 정리" 화면이 읽는
`library_asset_id`(자료실) 세계와 원래 다른 표였다. 그리고
`footage_organizer.py`(2026-08-12부터)가 이미 같은 `AutoCutPlanner`로 장면
분석을 돌리고 있어서, 이 둘을 직접 잇는 것보다 **raw_video를 자료실에도
등록**하는 쪽이 훨씬 적은 코드로 "촬영본 정리"의 전체 기능(장면 나누기·
제외·적용·파생 렌더)을 그대로 물려준다 — owner가 셋 중 "촬영본 정리
화면과 통합"을 선택.

**한 일**: `/api/projects/{id}/source-video/upload`(찍어 둔 영상으로
시작하는 길)에서 raw_video 등록 직후, 이미 있는 `LibraryIngestService`로
같은 파일을 자료실에도 등록(content-sha256 기반, `library_assets.py`가
쓰는 것과 같은 인스턴스). 연결은 프로젝트 자산 메타데이터에도 남겨
새로고침 뒤에도 살아 있다. "찍어 둔 영상으로 시작" 화면에 "촬영본
정리에서 장면 나누기" 링크가 뜬다(`/footage?library_asset_id=...`).
등록 실패는 조용히 건너뛴다 — 대본 만들기가 핵심이고 자료실 등록은
덧붙이는 편의.

**검증**: RED 드릴 셋(백엔드·프론트 성공 표시·프론트 링크) 통과, 전체
pytest(4812)+전체 vitest(1605) 단독 실행 통과, 컨테이너 재빌드 뒤 curl로
실제 영상을 올려 실제 Whisper 받아쓰기·실제 자료실 등록까지 확인하고,
브라우저로 "촬영본 정리에서 장면 나누기" 링크를 실제로 눌러 그 촬영본이
자동 선택된 채 열리는 것까지 확인.

**의도적으로 안 한 것**: 이 세션 이전에 이미 올라와 있던 raw_video
자산(예: `project-15ed00b1` "찍어둔 영상 시작 확인")은 자료실 연결이
없다 — 이번 변경은 업로드 시점에만 걸리는 앞으로만 적용되는 길이다.
과거 자산을 일괄로 자료실에 등록하는 소급 작업(migration)은 하지 않았다.
`auto-cut-plan`/`auto-cut-detect` 엔드포인트 자체는 지우지 않고 그대로
남겨 뒀다(호출자가 없어도 삭제는 이번 요청 범위 밖).

  않는지. **다른 트랙끼리 같은 시각은 정상**이다(브롤 위에 음악).
- `migrate_segment_media_to_placed_clips(...)` -- 지금 세그먼트에 달린
  선택을 놓인 클립으로 **읽어만** 낸다. 판정 규칙의 정본은
  `composition_plan.py`(:526-583)이고 그 분기를 그대로 옮겼다.
- `build_track_registry_snapshot(session)` -- Phase 1+2를 한 번에.
  Phase 4·5·6·7이 실제로 부를 자리다.

### 8.2 그 과정에서 찾은 진짜 결함 (같이 고침)

**장면 둘을 합치면 골라 둔 브롤·음악·효과음이 조용히 사라졌다.**
합치기 전에는 정상 렌더되던 것이, 합친 뒤에는 실제 렌더 결과가 0건이었다
(`materialize_editing_session_timeline`으로 직접 확인).

원인: 합치기는 직접 선택을 일부러 지우고 창(`media_windows`)에 권한을
넘긴다(코드 주석이 그렇게 말한다 -- 한쪽 선택이 다른 쪽 구간까지 늘어나지
않게 하려고). 그런데 직접 선택을 고르는 순간 그 필드는 창에서 지워지고
(`_clear_windowed_media_override`), `_media_windows()`는 이미 있는 창을
그대로 돌려준다. 그래서 넘길 것이 창에 없어 선택이 통째로 없어졌다.

수정: `_effective_media_windows()`를 새로 두어, 합치기 전에 직접 선택을
창에 접어 넣는다(직접 선택은 세그먼트 전체에 걸리므로 모든 창에 같은 값).
`editing_session.py` 한 곳(merge)만 이 함수를 쓴다.

시험 넷을 `tests/test_editor_timeline_mutations.py`에 넣었다 -- 잃어버리지
않는지, 한쪽만 있을 때 **합친 구간 전체로 늘어나지도** 않는지(반대 방향의
같은 결함), 세 조각을 두 번 합쳐도 오프셋이 제대로 쌓이는지.

### 8.3 초록인데 아무것도 안 지키던 시험 (기록해 둘 것)

Phase 2의 핵심 시험은 "새 모델이 실제 렌더러와 같은 말을 하는가"인데,
처음 썼을 때 **창 오프셋을 통째로 무시하게 고쳐도 초록이었다.** 쪼개기만
하면 창 오프셋이 늘 0이라 그 차원을 한 번도 안 밟았기 때문이다. 0이 아닌
오프셋은 **합치기**가 만든다 -- 시험을 합치기까지 지나가게 고치고 나서야
드릴이 빨간불이 됐다. 그 김에 위 결함도 나왔다.

교훈은 CLAUDE.md가 이미 아는 것이지만 값이 비쌌으니 다시 적는다:
**드릴이 빨간불이 안 뜨면 시험을 늘리기 전에 그 분기에 실물이 닿는지부터
봐라.**

### 8.4 Phase 5를 만들 사람이 알아야 할 것

- **효과음만 `source_action_id`를 갖는다.** 유진 추천을 owner가 거절했는지
  되짚는 열쇠라(`composition_plan.py`가 `rejected_sfx_action_ids_by_segment`로
  거른다) 셋을 대칭으로 다루면 조용히 사라진다. `PlacedClip`에 선택
  필드로 명시해 뒀고 시험으로 고정했다.
- **되돌리기(undo/redo)가 아직 이 모델을 모른다.** `editing_transactions.py`의
  `_snapshot()`은 `segments`·`caption_style`·`timeline_placement_overrides`
  **세 개를 이름으로 적어** 담는다. Phase 2는 쓰는 문을 안 만들었으므로
  지금은 문제가 없지만, Phase 5가 이 모델에 직접 쓰기 시작하면 그 자리를
  같이 넓혀야 한다 -- `timeline_placement_overrides`를 넣을 때 이미 한 번
  했던 일이다.

## 9. Phase 6(CapCut 내보내기 일반화)은 지금 하지 않는다 (2026-09-10 조사 결론)

"결정 없이 바로 시작 가능"으로 적혀 있던 단계인데, 실제 코드를 읽어 보니
**지금 하면 존재할 수 없는 입력을 위한 일반화**가 된다. 직접 확인한 근거:

- `composition_plan.py`의 `materialize_editing_session_timeline`은 클립을
  `tracks: dict[kind, clips]`로 모아서 마지막에 **종류당 정확히 한 트랙**으로
  펴서 내보낸다(:703-711). 이 함수가 **ffmpeg 렌더러와 CapCut 내보내기의
  공통 상류**다. 내보내기를 아무리 일반화해도 들어오는 타임라인이 이미 접혀
  있다.
- 애초에 두 번째 브롤 트랙을 만들 방법이 없다(Phase 5가 아직 없다).
- CapCut 내보내기는 필수 단계가 아니라 **선택적 호환·비상 경로**다
  (CLAUDE.md §2.1).

그래서 Phase 6은 **Phase 4(공통 상류가 `track_id`를 끝까지 들고 가게) →
Phase 5(트랙을 실제로 추가할 수 있는 문) 뒤**로 미룬다. 지금 하면 아무
생산자도 안 내놓는 손으로 지은 타임라인을 상대로 시험을 쓰게 되는데, 그건
초록인데 owner 화면은 그대로인 §4의 그 실패다.

### 9.1 그 조사에서 같이 나온 것 (Phase 4·5가 알아야 함)

- **같은 종류 트랙 둘이 생기면 CapCut 쪽에서 진짜로 깨지는 자리**:
  `pycapcut/track.py`가 한 레인 안 겹침을 예외로 막으므로(두 브롤을 한 레인에
  펴면 겹치는 순간 내보내기 실패), 트랙 이름이 유일해야 하고
  (`NameError`), `previous_broll_segment`가 브롤 루프 전체에 걸린 **단일
  변수**라 전환이 엉뚱한 트랙의 마지막 조각에 붙는다. CapCut 형식 자체는
  같은 종류 트랙 여럿을 지원한다 -- 막고 있는 것은 우리 어댑터다.
- **`track_states.py`는 종류(kind)로 키를 잡는다**(:50, :98). 트랙별
  숨김/음소거는 지금 구조로 **표현 자체가 안 된다** -- 같은 종류 트랙 둘 중
  하나만 숨기려면 `track_id` 키로 바꿔야 하고, 그건 세션 저장 스키마 변경 +
  화면 의미 결정이다. **로드맵의 "결정 필요: 없음"은 여기서 틀렸다.**

### 9.2 그래서 owner 결정이 더 필요하다 (로드맵의 넷에 더해)

5. 같은 종류 트랙이 여럿일 때 **숨김/음소거를 트랙별로** 할지(스키마 변경),
   지금처럼 종류 단위로 둘지.
6. CapCut이 감당 못 할 만큼 트랙이 많을 때 **펴서 내보내고 경고**할지,
   거절할지(`capcut_compatibility_warnings` 통로는 이미 있다).
7. 트랙 이름이 CapCut 화면에 그대로 보인다 -- 이름 충돌 규칙과 §10.13
   창작자 언어 규정을 어떻게 맞출지.
8. `Track.order`를 CapCut 레이어 순서에 그대로 매길지, 겹칠 때 무엇이 위로
   갈지.

## 10. Phase 4 첫 조각 -- 조용한 클립 유실만 먼저 막았다 (2026-09-10)

Phase 4("ffmpeg 렌더러 일반화")를 통째로 하지 않고, **결정 없이 할 수 있는
부분만** 떼어 먼저 했다.

### 10.1 고친 것

`composition_plan.py`가 클립을 종류로 모을 때 `tracks[track_type] = clips`로
**덮어썼다**. 같은 종류 트랙이 둘이면 앞 트랙 클립이 통째로 사라진다 --
예외도 경고도 빈 자리도 없이. `setdefault(...).extend(...)`로 바꿨다.

오늘 입력(`timeline_builder`가 종류당 한 트랙)에서는 **완전한 무동작**이다.
Phase 5가 트랙 추가 문을 열면 그때 실물이 닿는다.

### 10.2 일부러 안 한 것과 그 이유

- **z-order(어느 트랙이 위)**: 지금 규칙은 "늦게 시작한 것이 위, 같으면
  clip_id 문자열 순"이다(`ffmpeg_final_renderer.py`가 정렬해 차례로 얹는다).
  캡컷은 "위 트랙이 위"다. 바꾸면 **겹치는 클립이 있는 기존 편집본의 결과
  그림이 달라진다** -- 리팩터링이 아니라 눈에 보이는 제품 변경이다.
- **트랙 정체성 끝까지 들고 가기**(`CompositionItem`에 `track_id`/`order`):
  z-order를 정하지 않으면 들고 가 봐야 쓸 데가 없다. 게다가
  `canonical_dict()`는 `fingerprint_exact_preview`가 먹으므로 필드를 늘리면
  **캐시된 미리보기가 전부 무효**가 된다 -- 넣더라도 기본값일 때 출력이
  안 바뀌게 해야 한다.
- **내레이션 다중 트랙**: `composition_plan.py`는 배치를 전부 내레이션
  세그먼트에서 끌어낸다. 내레이션 트랙이 여럿이 되는 것은 Phase 3(타이밍
  기준) 결정이 나와야 한다 -- Phase 4가 그걸 몰래 전제하면 안 된다.

### 10.3 Phase 4를 이어서 할 사람에게

Phase 4 나머지는 **owner 결정 하나(z-order)에 전부 걸려 있다.** 그것만
정해지면 순서는 이렇다: 트랙별 `clip_id` 충돌 방지(트랙이 하나일 때는
지금과 **바이트 단위로 같은** id를 유지해야 미리보기 캐시가 안 깨진다) →
`CompositionItem`에 트랙 정보 → 정렬 키에 트랙 순서 → `_timeline_from_plan`
트랙별 재구성 → 옛 concat 경로에 fail-closed 울타리.

**안전망**: 지금 입력에는 전부 무동작이므로, 대표 타임라인 하나로
`canonical_dict()`와 생성된 `filter_complex` 문자열이 **바이트 단위로 같은지**
보는 등가 시험이 깃발보다 싸고 강하다.

## 11. Phase 4 갭검증 (2026-09-10) -- 계획 대비 안 한 것을 정직하게 적는다

owner 지시로 계획 단계와 실제로 한 것을 하나씩 대조했다. **한 것보다 안 한
것이 더 중요하다** -- 다음 사람이 "Phase 4는 끝났다"고 믿고 그 위에 쌓으면
안 되기 때문이다.

### 11.1 한 것

- 같은 종류 트랙 둘일 때 앞 트랙 클립이 사라지던 것(덮어쓰기 → 모으기)
- 겹칠 때 위 트랙이 위로(브롤 합성 정렬에 트랙 순서 반영)
- `CompositionItem.track_order` + 지문 보호(`_canonical_item`)

### 11.2 안 한 것 (실물에 안 닿아서 미룸, 그러나 남아 있음)

**전부 "같은 종류 트랙이 둘 이상일 때만" 문제가 된다.** 오늘은
`timeline_builder.py:198-204`가 종류당 정확히 하나씩만 만들어서
(`narration_primary`·`broll_overlay`·`music_bed`·`sfx_overlay`) 실물이
안 닿는다 -- 이게 이번 변경들이 무동작인 근거이기도 하다.

1. **오버레이 합성이 아직 옛 정렬**(`ffmpeg_final_renderer.py:1202-1204`).
   브롤은 트랙 순서를 보는데 오버레이는 안 본다. 오버레이 트랙이 둘이
   되면 위아래가 뒤집힌다. 브롤과 **같은 한 줄 고치기**면 된다.
2. **전환 짝짓기가 트랙을 안 가린다**(`:308-311`). 시간상 붙어 있는 브롤
   클립을 짝지어 전환을 거는데, 트랙이 둘이면 **다른 트랙 클립끼리** 짝이
   될 수 있다. 트랙별로 나눠 짝지어야 한다.
3. **세션 유래 클립 이름이 충돌한다**(`composition_plan.py:569`,
   `session-{종류}-{세그먼트}-{창번호}`). 같은 세그먼트에서 두 트랙이
   나오면 이름이 같아진다. 렌더러가 이름으로 입력을 찾으므로
   (`:1550` `source_indices[item.clip_id]`) 하나가 다른 하나를 가린다.
   **트랙이 둘 이상일 때만 접미사를 붙여야** 한다 -- 항상 붙이면 지금
   편집본의 이름이 바뀌어 미리보기 캐시가 깨진다.
4. **`_timeline_from_plan`이 다시 종류로 접는다**(`:1424`
   `tracks.setdefault(item.track_type, ...)`). 계획에서 타임라인을 되돌릴
   때 트랙 정체성이 다시 사라진다.
5. **옛 concat 경로에 울타리가 없다**(`:2242-2264`). 계획을 안 쓰는 옛
   경로에 멀티트랙 타임라인이 들어오면 두 트랙을 이어 붙여 **길이가 두 배인
   영상**을 만들 수 있다. 조용히 틀리느니 막아야 한다.

### 11.3 일부러 안 바꾼 것

`composition_plan.py:985`의 `items` 정렬은 **그대로 둔다**. 이 순서가
`canonical_dict()`에 그대로 실려 미리보기 지문이 되므로, 바꾸면 지금 있는
편집본의 캐시가 전부 무효가 된다. 렌더러가 어차피 자기 기준으로 다시
정렬하므로 z-order에는 영향이 없다.

### 11.4 Phase 5 착수 전에 정해야 할 것

Phase 5(트랙 추가·삭제·순서 API)는 **쓰는 문**이라 아래가 먼저 정해져야
한다 -- Phase 2·4는 읽기만 해서 피해 갈 수 있었다.

- **되돌리기**: `editing_transactions.py:13-18`의 `_snapshot()`이 담는
  최상위 열쇠는 `segments`·`caption_style`·`timeline_placement_overrides`
  **셋뿐이고 이름으로 적혀 있다.** 트랙 목록을 세션에 새로 저장하면 그
  자리를 같이 넓혀야 되돌리기가 트랙 추가·삭제를 함께 되돌린다.
  (`timeline_placement_overrides`를 넣을 때 이미 한 번 했던 일이다.)
- **트랙별 숨김/음소거**: `track_states.py`가 종류로 키를 잡아서 같은 종류
  트랙 둘 중 하나만 숨기는 것이 **표현 자체가 안 된다**(§9.1). 세션 저장
  스키마 + 화면 의미 결정.
- **추가·삭제 UX와 개수 상한**, **타이밍 기준 트랙을 지울 때의 동작**(§3의
  결정 1·2)도 그대로 남아 있다.

## 12. Phase 3·7 결정과 순서 정정 (2026-09-10)

owner가 "나머지 결정 사항도 추천으로 진행해"라고 판단을 위임했다. 코드를
직접 읽고 정한 것과 그 근거를 남긴다.

### 12.1 Phase 3(타이밍 기준 일반화)은 **하지 않는다**

로드맵 §3의 owner 결정 1·2번은 둘 다 **도달할 수 없는 상황**을 다룬다.

- **내레이션 트랙을 늘릴 방법이 없다.** `session_tracks.ADDABLE_TRACK_KINDS`가
  `{broll, bgm, sfx}`뿐이고, 이건 Phase 5에서 일부러 그렇게 막은 것이다
  (내레이션이 여럿이면 "무엇이 세그먼트 시간을 정하는가"가 흔들린다).
  기준 트랙이 하나뿐이면 "기준 트랙을 지우면?"이라는 질문 자체가 안 선다 --
  마지막 줄은 이미 못 지운다.
- **자막은 트랙이 아니다.** 세그먼트의 `caption_text` 필드와 `content_windows`에
  산다(`editing_session.py:91,:106-111,:479`). `timeline.tracks` 안에 자막
  트랙이 실리지도 않는다(`editor_playback_manifest.py:104` 주석이 같은 말을
  한다). 그러니 "자막 트랙이 가리키던 내레이션 트랙" 이라는 주어가 없다.

제품 쪽으로도 근거가 있다. 내레이션 트랙 둘은 **두 목소리가 동시에 말하는
것**을 뜻한다. 1인칭 내레이션 + B-roll 콘텐츠에는 쓸 자리가 없고, "여러 번
녹음해서 고르기"는 이미 다시-찍기 후보가 맡고 있다.

**Phase 6과 같은 판단이다** -- 존재할 수 없는 입력을 위해 일반화하지 않는다.
내레이션 트랙을 늘리기로 결정하는 날 이 결정을 다시 연다. 그때의 권장값은
로드맵대로 (a)+(b)다: 기준 트랙은 못 지우고, 다른 트랙을 먼저 기준으로
지정해야 지울 수 있다. (c)("그 순간 값으로 얼리기")는 되돌릴 수 없는 상태를
조용히 만들기 때문에 권하지 않는다.

### 12.2 Phase 7보다 먼저 할 것이 있었다 -- Phase 2b

Phase 7(타임라인 UI)을 쓰려고 코드를 읽다가 **더 앞의 구멍**을 찾았다.

`composition_plan.py:612`(당시)에서 촬영본/음악/효과음 클립은 전부 장면에
달린 필드(`broll_override` 등)에서 나와 `tracks[종류]` 바구니 **하나**로
쏟아졌다. 클립이 "나는 몇 번 트랙 소속"이라고 말할 자리가 아예 없었다.

즉 **Phase 5로 트랙을 추가해도 거기 올릴 수 있는 것이 없다.** 그 상태로
화면 줄부터 만들면 아무것도 못 올리는 빈 줄이 하나 늘어난다.

그래서 순서를 바꿔 Phase 2b를 먼저 했다(커밋 `9345ce826`):

- 바구니 열쇠를 `(종류, 트랙 이름)`으로 바꿨다.
- 장면 override의 `track_id`를 읽어 그 트랙으로 보낸다.
- 이름표가 없으면 그 종류의 **첫 트랙**으로 간다 → 지금 있는 편집본의
  결과가 한 글자도 안 바뀐다(미리보기 캐시 지문 보호).
- 이름표를 못 알아보면(지운 트랙·다른 종류·옛 흔적) **클립을 버리지 않고**
  첫 트랙으로 내린다. 재료는 여전히 장면에 붙어 있으므로 조용히 사라지면
  안 된다.
- 이름 충돌 검사는 바구니가 아니라 **종류 전체**에서 본다. 렌더러가 클립
  이름으로 입력을 찾기 때문이다(`source_indices[clip_id]`).

두 이름 세계가 만나는 자리를 조심할 것: 트랙 목록의 이름은 `track-broll`
(하이픈, `track_registry.migrate_legacy_tracks_to_registry`)이고 완성된
타임라인의 이름은 `track_broll`(밑줄, `timeline["tracks"]`)이다. 그 종류의
첫 트랙은 **옛 이름 그대로** 나와야 지문이 안 깨진다.

### 12.3 아직 못 쓴다 -- 쓰는 문이 없다

Phase 2b는 **읽는 쪽**만 열었다. `track_id`를 실제로 적어 넣는 API가 없다.
그리고 여기서 설계상의 벽을 하나 확인했다:

**장면 하나에 촬영본은 하나뿐이다.** `broll_override`는 단수이고,
`media_windows`는 겹쳐 놓는 층이 아니라 **쪼개기/합치기가 매체 권한을
보존하려고 쓰는 구간 분할**이다(`_slice_media_window_basis`가 구간으로
자른다). 그러니 `media_windows`에 겹치는 창을 밀어 넣는 것은 지원되는
모양이 아니다 -- `tests/test_clip_track_assignment.py`의 겹침 시험은 엔진
바구니 동작을 재는 단위 시험일 뿐, owner가 밟을 수 있는 길이 아니다.

**같은 시간에 촬영본 둘을 겹치려면 배치(placement) 목록이 필요하다** --
Phase 2(`clip_placement.py`)가 이미 모델링해 둔 바로 그것이다. 그건 세션에
새 최상위 열쇠를 더하는 일이고, 저장 화이트리스트
(`local_project_store.py`)와 되돌리기 스냅샷(`editing_transactions._snapshot`)
을 같이 넓혀야 한다. 쪼개기/합치기가 배치를 어떻게 데리고 다닐지도 정해야
한다.

### 12.4 Phase 7 첫 조각의 모양 (아직 안 만듦)

만들 때의 결정은 이렇게 정했다.

- **줄을 `TIMELINE_LANES`가 아니라 세션 트랙 목록에서 뽑는다.**
  지금은 `timeline-geometry.ts:3`의 여섯 줄이 코드에 박혀 있고

- **옛 다섯 역할의 y 좌표는 한 픽셀도 안 움직여야 한다.**
- **트랙별 숨김/음소거도 Phase 7에서 같이 한다.** 미뤄 뒀던 이유가
  `TimelineDock.tsx:257-266`의 **전체 교체 payload**였는데, 그 화면을 고치는
  순간 그 이유가 사라진다. 지금 상태로 track_id별 상태를 만들면 옛 화면이

- **줄 순서는 위/아래 버튼으로.** 세로 드래그는 새 제스처가 필요하고 기존

### 12.5 Phase 7 첫 조각 -- 줄 좌표만 데이터에서 받게 했다

`timeline-geometry.ts`의 `deriveClipRect`에 **줄 목록**을 넘길 수 있게 했다.

- 클립에 `trackId`가 붙으면 그 줄, 없으면 그 종류(`lane`)의 줄.
- **모르는 이름표는 그 종류의 줄로 내린다.** 엔진(12.2)과 같은 규칙이다.
  여기서 `RangeError`를 던지면 지운 트랙의 이름표가 남아 있다는 이유만으로
  **작업판 전체가 죽는다**(`requireClip`은 종류만 검사하도록 그대로 뒀다).
- 줄 목록을 안 주면 예전 `TIMELINE_LANES` 여섯 줄 그대로다.

**아직 화면은 안 바뀐다.** `TimelineDock.tsx:773`은 여전히 `TIMELINE_LANES`로
줄을 그리고, 아무도 `rows` 인자를 넘기지 않는다. 다음 조각이 그것이다.

### 13.1 버튼만 열면 안 되는 이유 (owner 결정 필요)

게이트만 풀면 **조용히 잘못 도는 길이 둘** 열린다.

1. **소리가 안 실린다.** 오디오 그래프는 narration/broll(`:1361-1382`)과
   bgm/sfx(`:1383`)만 다루고 overlay 분기가 아예 없다. 얹은 영상은 무음이다.
2. **원본이 장면보다 짧으면 조용히 끝난다.** 길이 부족 검사는 broll에만
   있고(`composition_plan.py:997`) overlay엔 없다. `eof_action=pass`라
   오류 없이 중간에 사라진다.

이 저장소가 반복해서 값을 치른 것이 정확히 이 형태다(조용한 실패). 그래서
**버튼 게이트를 푸는 것은 소리 처리와 길이 검사를 정한 뒤**여야 한다.
또한 `docs/decisions/` 의 "사진 오버레이" 승인 범위를 넘는 확장이므로
owner 판단이 먼저다.

권장: (a) overlay 트랙 소리는 **기본 무음, 켤 수 있는 칸**(내레이션을 덮지
않는 것이 기본값이어야 한다), (b) 길이가 모자라면 broll과 **같은 방식으로**
막거나 늘린다, (c) 그 둘이 끝난 뒤 `EditorAssetBrowser.tsx:561` 게이트를
푼다.

### 13.2 게이트 둘을 열었다 -- 실물 렌더로 확인함 (2026-09-10, 커밋 `c43abf4b1`)

owner가 판단을 위임했고, 조사 결과 §13.1의 걱정 둘 중 하나는 **결함이
아니었다**:

- **소리**: overlay 트랙에 오디오 분기가 없는 것은 맞다. 그런데 **기본 무음이
  올바른 기본값**이다 -- 얹은 영상 소리가 내레이션을 덮으면 그게 사고다.
  "이 영상 소리도 같이"는 나중에 칸으로 더할 것이지 지금 막을 이유가 아니다.
- **길이**: 얹은 영상이 장면보다 짧으면 제 길이만큼 나오고 사라진다
  (`eof_action=pass`). 이건 조용한 실패가 아니라 **캡컷과 같은 자연스러운
  동작**이다. 남는 것은 타임라인 표시가 장면 전체를 덮는 것처럼 보이는 것뿐
  (Phase 7에서 같이 볼 것).

그래서 게이트 둘을 열었다.

1. `EditorAssetBrowser.tsx` -- `previewKind`가 `image`뿐이던 것을
   `image | video`로. 소리 자산은 그대로 제외(화면에 그릴 것이 없다).
2. `yujin_editing_proposal_adapter.py` -- `_OVERLAYABLE_ASSET_TYPES`
   (`image`, `broll_video`). 자산 안내문도 같이 고쳤다 -- **목록과 안내문은
   한 쌍**이라, 받게만 해 놓으면 유진은 안 고른다.

**역방향 검증(실물)**: 살아 있는 컨테이너에서 바다 영상을 화면으로 깔고 그
위에 시험 패턴 영상을 `top/right/small`로 얹어 실제 mp4를 렌더했다.

- 렌더 `succeeded`, 720x404 / 5초 / 150프레임
- 0.3초와 2.0초 프레임을 뽑아 **눈으로 확인**: 오른쪽 위 인셋 안의 숫자
  카운터가 넘어가 있다 -- **정지 프레임이 아니라 재생 중**이다.

이것이 중요한 이유: "렌더가 성공했다"만으로는 한 프레임만 얼려 놓은 것과
구별이 안 된다. 이 저장소가 이미 그 자리에서 틀린 적이 있다.

### 14.3 검토가 잡은 것 — 혼자 했으면 놓쳤을 것들

- **렌더를 통째로 죽일 수 있는 한 줄이 무방비였다.** `ffmpeg_final_renderer.py:1573`
  (소리 스트림 없는 오버레이 입력을 추려 두는 자리)을 지워도 시험이 전부
  초록이었다. 사진을 얹고 소리를 켜면 `[N:a]`가 그래프에 들어가 **완성본이
  통째로 실패**한다. 기존 시험은 `soundless_source_clip_ids`를 손으로 넣어
  **쓰는 쪽만** 재고 있었다 — 변형 탐침이 만드는 쪽과 쓰는 쪽을 구분하지
  못한 것이다. 실물 렌더를 지나는 시험을 넣고, 재검토자가 그 줄을 직접
  지워 렌더가 죽는 것을 확인했다.
- **유진은 사진에도 소리를 켤 수 있었다.** 화면은 사진에 그 칸을 일부러
  안 띄우므로, 켜지면 보이지도 끄지도 못한다 — `[[videobox-catalogue-and-current-value-are-a-pair]]`
  가 말한 "되돌리기가 막힌다"와 같은 모양. 안내문에서 빼고 검증에서도 거절한다.
- 까다로운 순회 로직이 세 곳에 복사돼 있던 것(`_iter_matching_overlay_containers`로 통합),
  화면 문구가 두 벌이 된 것, 서버로 가는 다리에 지키는 시험이 없던 것.
- 화면이 보내는 명시적 `false`가 출력은 그대로인데 **미리보기 캐시 지문을 깼다.**

하면 앞서 정한 자리가 조용히 사라짐)은 계획서
`docs/superpowers/plans/2026-09-11-overlay-presets-not-silently-erased.md`로
고쳤다. 다음 세션이 같은 결함을 다시 만들지 않으려면 이 계약을 먼저 읽을 것.

**고친 계약(세 상태)**: `update_segment_image_overlay`의 프리셋 넷(`vertical`·
`horizontal`·`size`·`motion`)은 이제 세 상태를 받는다.

| 부르는 쪽이 하는 것 | 뜻 |
|---|---|
| 인자를 아예 안 줌(엔진 기본값 `_KEEP`) | 지금 저장된 값을 그대로 둔다 |
| `None`/`null`을 줌 | 지워서 "안 고름"으로 되돌린다 |
| 값을 줌 | 그 값으로 바꾼다 |

이게 앞서 "같이 못 고친 이유"로 적었던 문제(`None`을 "안 말함"으로 바꾸면
"가운데로 되돌려줘"라고 말할 방법이 없어진다)를 푼 방식이다 -- "안 말함"과
"`None`"을 하나로 접지 않고 **셋으로 갈랐다.** API 스키마는
`ImageOverlayRequest.preset_overrides()`가 pydantic v2의 `model_fields_set`으로
"칸이 아예 없음"과 "칸이 있는데 값이 `null`"을 구분해서 세 상태를 엔진까지
그대로 옮긴다. 화면(`InspectorControls.tsx`)의 `안 고름` 선택지가 명시적
`null`을 보내는 길이고, 유진 안내문(`yujin_editing_proposal_service.py`)도
같은 세 상태를 말로 설명한다.

**결정된 부수 효과 하나** — 결함이 아니라 owner 승인된 의도: 엔진은 세그먼트
하나당 이미지 오버레이를 최대 하나만 두므로, 프리셋이 있는 장면에 **새 자산**을
프리셋 없이 얹으면(자산 목록 `화면에 얹기`, 유진 후보 적용 둘 다 이 길) 새
자산이 앞 자산의 자리·크기·움직임을 그대로 물려받는다. 그림창(PIP)에서 화면만
바꿔도 액자 위치는 그대로인 것과 같은 기대라 그대로 두기로 했다. 고정 시험은
`tests/test_overlay_presets_are_not_erased.py`의
`test_a_new_asset_over_the_same_scene_inherits_the_old_frame`.
