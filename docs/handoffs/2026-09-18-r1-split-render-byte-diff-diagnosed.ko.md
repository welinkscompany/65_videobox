# task_006f1523 -- R1 경계 나누기가 완성본 바이트를 바꾸는 이유를 끝까지 찾았다 (고치지는 않았다)

owner 승인(2026-09-18, "근본적으로 확인하고 고쳐줘") 위에서
`tests/test_short_form_split_does_not_change_master_bytes.py`의 xfail이 고정해
둔 실측을 끝까지 추적했다. **원인은 확정했다. 고치는 것은 이번 세션에서
하지 않기로 판단했다** -- 이유는 아래 "왜 고치지 않았나"에 있다.

## 원래 가설은 틀렸다

2026-09-13에 적어 둔 가설(세그먼트가 둘로 나뉘면서 같은 소스를 두 번째
`-i`로 다시 여는 트림 경계 계산이 서브프레임 단위로 어긋난다)은 **틀렸다.**
ffmpeg `showinfo` 필터로 프레임 체크섬을 직접 뽑아 확인했다 -- 나눈 뒤 오른쪽
조각이 `-ss 0.75 -copyts -i`로 다시 여는 소스도, 나누기 전 연속 디코드도
**같은 절대 시각의 프레임은 체크섬까지 완전히 같다.** 트림·오프셋 계산은
정확하다.

## 진짜 원인 -- 필터 그래프 모양(topology)이 바뀐다

장면을 나누면 왼쪽·오른쪽 조각이 같은 원본(같은 b-roll, 같은 내레이션
파일)을 가리켜도 `composition_plan.py`가 이 둘을 **서로 다른 클립**으로
만든다 (`clip_id`가 `session-broll-{segment_id}-0`처럼 `segment_id`를 물고
있어서, 나뉜 조각은 자동으로 다른 이름을 받는다). 그 결과
`ffmpeg_final_renderer.py`가 만드는 필터 그래프에 `overlay`/`atrim`/`amix`
단계가 **하나 더** 쌓인다 -- 실측(합성 자산, 2문장 대본):

- 나누기 전: `canvas0 -> overlay(broll 전체) -> canvas1 -> overlay(broll_002) -> canvas2 -> vout`,
  내레이션 `amix=inputs=2`.
- 나누기 뒤: `canvas0 -> overlay(broll 왼쪽) -> canvas1 -> overlay(broll 오른쪽, 새 입력) ->
  canvas2 -> overlay(broll_002) -> canvas3 -> vout`, 내레이션 `amix=inputs=3`
  (실제 캡처한 두 ffmpeg 명령을 직접 대조해 확인).

같은 화면 내용이라도 필터 그래프의 **모양**이 다르면 손실 인코더(libx264,
AAC)가 다른 비트를 낸다 -- 이건 렌더러의 버그가 아니라 손실 재인코딩의
본질적 성질이다. 격리 실험으로 직접 확인했다:

1. 똑같은 필터 그래프 명령을 **두 번** 돌리면 -- 바이트가 완전히 같다
   (결정적, 대조군).
2. 같은 화면 내용을 `overlay` 단계 **하나 더** 거치게만 만들면(합성 원본을
   0~1.5초로 한 번에 얹는 그래프 vs 0~0.75초·0.75~1.5초로 나눠 얹는 그래프,
   PTS 오프셋 계산은 둘 다 정확하게 맞췄다) -- 디코드해서 프레임 단위로
   PSNR을 재면, 대부분 프레임은 40~55dB(재인코딩 잡음 수준, 대표님이 이미
   육안으로 "문제없다"고 본 수준과 일치)지만 fps 격자에 걸치는 접합부 근처
   프레임 한두 개는 PSNR이 7~27dB까지 떨어진다(진짜 프레임 어긋남 -- 이
   부분은 육안으로도 보일 수 있는 수준이라 완전히 무해하다고 단정하지는
   않는다).

즉 "나누기가 렌더 바이트를 안 바꿔야 한다"는 R1의 원래 주장은, **지금의
"캔버스 위에 클립마다 `overlay`를 쌓는" 합성 방식**에서는 구조적으로 지키기
어렵다 -- 나뉜 조각이 같은 소스의 이어지는 구간이라는 사실을 필터 그래프를
만들기 **전에** 감지해서 하나로 다시 합치지 않는 한, 인코더 잡음까지
완전히 없앨 수 없다.

## 왜 고치지 않았나

진짜 고치려면 `composition_plan.py`의 클립 생성 로직(브롤·내레이션·bgm·
sfx 넷 다 각자 클립을 만든다)에 "인접한 두 클립이 같은 원본의 이어지는
구간이면 필터 그래프를 만들기 전에 하나로 합친다"는 병합 단계를 새로
끼워 넣어야 한다. 이건 배속·되풀이(`loop`)·전환·2026-09-17~18에 막 들어온
자유 멀티트랙 Phase 5(트랙 추가/삭제/순서)와 전부 맞물리는 자리이고,
**`ffmpeg_final_renderer.py`·`composition_plan.py`는 모든 완성본 렌더가
지나는 자리**다 -- 여기서 병합 경계 조건을 하나라도 놓치면 블라스트 반경이
이 세션에서 고친 다른 어떤 결함보다 크다.

반대쪽 논리도 검토했다: "고치면 완전한 R1 준수, 재작업 회피"라는 장점은
있지만, 리스크 대비 이득이 낮다고 판단했다 -- 대표님이 이미 나누기 전/후
프레임을 육안으로 비교해 "별 문제 없어 보인다"고 답했고(이번 실험의
40~55dB PSNR 구간과 일치하는 판단), 이 task 자체가 오늘 승인 전까지
"안 급함"으로 미뤄져 있던 항목이다. 무리한 구조적 변경보다 정확한 진단을
남기는 쪽이 이 저장소의 명시적 우선순위(`CLAUDE.md` "정확성을 동의보다
우선한다", "정확한 진단이 더 가치있다")에 맞는다고 판단했다.

**예외적으로 남겨 둘 위험**: 접합부 근처 PSNR 7~27dB 프레임은 "완전히
무해"까지는 확인하지 못했다 -- 합성 테스트 자산(움직이는 패턴)이라 실제
영상에서도 같은 수준으로 보일지는 실측하지 않았다. 실제로 눈에 띄는 사고가
보고되면 이 문서와 아래 "다음에 손댈 자리"부터 다시 보면 된다.
