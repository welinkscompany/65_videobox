# 대본에 맞는 그림이 붙었고, 거기서 당나귀가 나왔다

- 작성: 2026-08-21
- 앞 문서: `2026-08-20-videobox-real-video-and-the-editor-look.ko.md`
- 개발선: `codex/videobox-container-compatibility`

## 무엇이 붙었나

앞 인계가 시킨 것 — ComfyUI provider → API → 화면 — 을 끝까지 붙였고, **완성본 mp4까지
나오는 것을 실제로 확인했다.**

owner 경로는 이렇다. 초안 준비가 "장면을 보여 줄 영상이 없어요"라고 말하는 자리마다
그 장면의 대본 한 줄이 깔린 설명 칸과 `그림 만들기` 버튼이 함께 뜬다. 누르면 그림이
만들어지고, 초안 준비가 다시 돌아 그 장면이 채워진다.

| 자리 | 무엇 |
|---|---|
| provider | `videobox_provider_interfaces/comfyui_image_generation.py` |
| 그림→자산 | `videobox_core_engine/scene_image_service.py` |
| 프롬프트 | `videobox_core_engine/scene_image_prompt.py` |
| API | `POST/GET /api/projects/{id}/scene-images` |
| 화면 | `features/media/SceneImageStudio.tsx` (기획 화면의 공백 장면마다) |

## 이 산책에서 나온 것

**1. 한국어를 그대로 넣으면 당나귀가 나온다.** 배관이 다 맞는데 그림만 틀리는 자리였다.
같은 씨앗(606386459)·같은 설정으로 두 번 쟀다.

| 넣은 말 | 나온 것 |
|---|---|
| `자막은 따로, 음악도 따로 붙입니다` | **픽셀아트 당나귀 두 마리** |
| 같은 뜻의 영어 묘사 | 실제로 그 장면 |

증거는 `artifacts/scene-image-check/korean.png`와 `english.png`다. FLUX의 글자
이해기(T5 + CLIP-L)는 영어로 배웠고, **한국어를 거절하지 않고 아무 그림이나 그럴듯하게
내놓는다.** 그래서 자산도 만들어지고 장면도 채워지고 테스트도 초록이다 — owner만 24초
뒤에 당나귀를 본다. 앞 인계의 "장면별 프롬프트(**유진이 쓴다**)"가 이 자리였는데,
처음에 배관만 보고 넘어갔다가 화면에서 그림을 열어 보고 알았다. **만든 것을 눈으로
열어 보지 않았으면 못 찾았다.**

지금은 한글이 섞여 있으면 유진이 영어 묘사로 다시 쓴다. 영어로 직접 적은 것은 건드리지
않는다. **닿지 않으면 거절한다** — 조용히 틀린 그림을 만드는 것은 실패하는 것보다 나쁘다.

**2. 그림 한 장을 자산 두 개로 넣는다.** `image` 하나와, 같은 그림을 담은 짧은 mp4
하나(`broll_video`). 렌더 경로가 B-roll 입력을 **영상으로** 열기 때문이다
(`ffmpeg_final_renderer.py`에서 broll 소스는 `is_image=False`로 들어가고
`_probe_media_duration`이 길이를 요구한다). PNG를 그 자리에 꽂으면 초안 화면까지는
멀쩡하고 **완성본에서 터진다.** 렌더 경로는 둘이라 한 곳만 고치면 같은 함정에 두 번
걸리므로, 렌더를 건드리는 대신 그림을 그 경로가 이미 아는 모양으로 바꿔 넣었다.

**3. 초안 준비가 그림을 엉뚱한 장면에 붙이고 있었다.** 준비는 B-roll을 **순서대로**
짝지어 왔다(`zip(segments, playable_broll)`). 촬영본은 어느 장면 것인지 아무도 안 적어
뒀으니 순서가 유일한 규칙이었지만, 만든 그림은 짝이 정해져 있다. 이제 `scene_segment_id`를
든 자산이 먼저 자리를 잡고 나머지가 남은 자리를 채운다. 대본을 고쳐 그 장면이 사라지면
**버리지 않고** 짝 없는 것과 똑같이 쓴다.

**4. nginx가 60초에서 자를 뻔했다.** 그림 한 장이 22~26초다. 업로드 1MB 벽과 같은
자리이고, 이 저장소의 테스트는 프록시를 한 번도 안 지난다. `proxy_read_timeout`을 앱
상한 위로 올리고, 두 값이 어긋나면 깨지는 테스트를 `test_compose_contract.py`에 뒀다.

## 실측 (RTX 5090, LM Studio 켜 둔 채)

| 잰 것 | 값 |
|---|---|
| 1280×720 · 20단계 (provider 직접) | 22.3초 |
| 같은 것, 프록시(5173)를 지나서 | 26.2초 |
| 유진이 프롬프트를 쓴 직후 한 장 | **87.9초** |
| 완성본 mp4 (15초, 1920×1080, 장면 4개) | 성공 |

**87.9초는 이유를 확정하지 않았다.** 유진의 두뇌(35B)가 방금 GPU를 썼을 때 잰
값이라 두 모델이 VRAM을 두고 겹쳤을 가능성이 크지만, 재서 확인한 것은 아니다.
**owner에게 "20초짜리"라고 말하지 마라** — 유진이 문장을 쓰는 경우가 기본 경로다.

## 확인한 것과 확인하지 못한 것

**확인한 것 (전부 도는 컨테이너에서, 프록시를 지나서)**

  (`artifacts/scene-image-check/final-frame-2s.png`)

**확인하지 못한 것**

- 세로(숏폼)로는 한 장도 만들어 보지 않았다. 코드 경로는 있고 시험도 있지만 실물은 없다
- 브라우저 스크린샷을 못 찍었다. Browser pane이 화면에 안 떠 있어서 픽셀이 안 그려진다.
  화면 확인은 접근성 트리와 DOM으로 했다
- owner 컨테이너에 시험용 프로젝트 `project-7ae9344d`(`그림 만들기 확인`)가 남아 있다.
  완성본 mp4가 들어 있으니 증거로 두었고, 필요 없으면 지워도 된다

## 얼굴 LoRA — 사진만 오면 된다

**앞 인계의 짐작 하나를 고친다. 학습 도구를 받을 필요가 없다.** 지금 깔린 ComfyUI
0.24.0에 학습 노드가 **이미 들어 있다**(노드 777개 중):

    LoadImageDataSetFromFolder → MakeTrainingDataset → TrainLoraNode → SaveLoRA

`loras` 폴더는 비어 있고 `clip_vision`도 비어 있다(2026-08-21 확인).

**owner 차례로 남은 것은 사진뿐이다.** 폴더를 만들어 두었다:

    D:\AI_Workspace_louis_office_50\20_project\65_videobox-project\drive-sync\내 얼굴 사진

어떤 사진이 좋은지는 그 폴더의 `여기에-사진을-넣어주세요.txt`에 적어 두었다.
옆의 `새 영상`·`새 음악`과 달리 **이 폴더는 자동으로 읽지 않는다** — 얼굴 학습은 한 번만
하면 되는 일이다.

사진이 들어오면 두 줄이면 끝난다.

```bash
.venv/Scripts/python.exe scripts/owner-path/train_face_lora.py
```

```bash
.venv/Scripts/python.exe scripts/owner-path/measure_face_likeness.py
```

두 번째가 앞서 만든 썸네일 프롬프트 셋에 얼굴을 세 가지 세기(0.7/0.9/1.1)로 얹고,
**얼굴 없이 만든 것과 나란히** 놓아 시간·닮은 정도 표를 찍는다.

**표의 숫자를 무엇으로 재는지 먼저 읽어라.** 이 기계에 얼굴 인식 모델이 없다
(`clip_vision` 비어 있음). 그래서 숫자는 **LM Studio에 올라온 눈 달린 모델의 판단**이고,
같은 그림을 세 번 물어 평균 낸 값이다. `일치율`이 아니라 `모델 판단`이라고 적는다.
**마지막 판단은 owner가 그림을 보고 한다** — 표는 어디부터 볼지 정해 줄 뿐이다.

학습 설정(1600단계·rank 16·학습률 0.0002)은 **실측이 아니라 출발점**이다. 한 번 돌린
뒤 그 값을 고쳐라. 사진이 10장보다 적으면 스크립트가 먼저 경고한다 — 그 결과를
"LoRA가 별로다"의 근거로 쓰면 틀린다.

**틀렸다.** 앞 인계(2026-08-20)에 그렇게 적혀 있었지만, 그 문서가 쓰인 **뒤**인
같은 날 20:52에 `3d9b72e7e feat: darken the editing screen`으로 들어갔다.
확인하지 않고 옮겨 적어서, 다음 세션이 이미 끝난 일을 하러 갈 뻔했다.

**인계에서 "남았다"고 읽은 항목은 옮겨 적기 전에 `git log -- <파일>`로 한 번
확인하라.** 인계 문서는 쓰는 순간 굳고, 그날 저녁 커밋은 거기 안 실린다.

승인 기록의 네 가지 중 실제로 남아 있던 것은 **항목 2(툴바)** 하나였고,
2026-08-21에 닫았다 — 큰 주황 알약 여덟 개를 조용한 회색 아이콘 단추로 내리고,

사람은 무엇인지 알 수 없고 읽어 주는 도구도 잃는다.
