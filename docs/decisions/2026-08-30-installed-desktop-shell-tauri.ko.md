## 확인한 것 — CapCut이 설치형인 이유와 VideoBox의 실제 구조 차이

CapCut(그리고 대부분 영상 편집기)이 설치형인 일반적 이유: 브라우저 밖 파일시스템
직접 접근, GPU 하드웨어 인코딩을 OS API로 직접 호출, 브라우저 탭 생명주기에
안 묶이는 백그라운드 처리, 오프라인 동작.

**VideoBox는 이 이유들이 이미 다른 방식으로 해결돼 있다.** 브라우저 탭은
제어판일 뿐이고, 실제 렌더링(FFmpeg)과 AI 생성(ComfyUI)은 이미 owner 로컬
머신에서 100% 서버 쪽으로 돈다(`2026-08-27` 문서가 확인한 것과 같은 결론 —
"웹이라 안 된다"는 전제가 아니라 이미 로컬로 도는데 창이 브라우저 탭이라는
껍데기 차이일 뿐). 그래서 설치형 전환이 주는 것은 CapCut이 얻는 파일접근·GPU
가속이 아니라: 앱 아이콘·독/작업표시줄 노출, 주소창 없는 창, 실수로 다른
페이지로 벗어나지 않는 것, 자동 시작 정도다.

**다른 사람에게 배포할 계획이 아직 없다.** 지금은 owner 1인용 로컬 도구다.
배포가 목표가 되면 Docker Compose 스택·별도 실행 중인 ComfyUI 의존성이
진짜 걸림돌이지, 창을 native로 바꾸는 것과 무관하다 — 이 결정은 그 문제를
풀지 않는다.

## 승인된 것

**Tauri로 얇은 데스크톱 셸을 만든다.** Electron이 아니라 Tauri를 고른 이유:
Electron은 Chromium을 통째로 번들링해(~120~200MB) 이미 Chrome을 쓰는 owner
환경에서 중복이고, Tauri는 OS 기본 webview(Windows는 WebView2)를 그대로
써서 훨씬 가볍다. VideoBox가 여러 사람에게 배포할 계획이 아직 없는 1인용
로컬 도구라는 점에서, 여러 OS의 Chromium 버전 통일성을 보장해야 하는
Electron의 장점이 필요 없다.

**범위: 창 셸뿐이다.** `scripts/owner-ready.ps1`이 띄운 컨테이너 스택
(`http://127.0.0.1:5173`)을 가리키는 native 창을 여는 것까지만. 렌더링·AI
생성·데이터 저장 로직은 전혀 건드리지 않는다 — 기존 웹 프론트엔드·백엔드
코드는 그대로 재사용한다(재사용 게이트 원칙, `CLAUDE.md` §3).

## 확인 필요 — 이 저장소가 아직 못 채운 것

**Rust 툴체인이 이 개발 머신에 없다.** Tauri는 Rust로 빌드된다. 스캐폴드
파일(설정·소스)은 만들 수 있지만, 실제로 빌드해서 화면에서 눌러 보는
검증(`CLAUDE.md` §4, "완료 = owner가 화면에서 실제로 쓸 수 있는가")은
Rust 설치 없이는 못 한다. Rust 설치는 시스템에 새 도구를 까는 일이라
owner 확인 후 진행한다.
